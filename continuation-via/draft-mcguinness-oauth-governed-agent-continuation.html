Identity Continuation Profile for Governed Agent Federation

Abstract

The OAuth 2.0 Profile for Governed Agent Federation carries a governed Agent Principal from an identity provider into one resource domain, as the actor of an Identity Assertion JWT Authorization Grant (ID-JAG) or the subject of a Workload Authorization Grant (WAG). A gateway that receives such an agent's request and calls resources in other domains for it holds neither the user's credential nor the agent's.¶

This document profiles the Identity Continuation Assertion for governed agents, with gateways as the primary deployment. The gateway obtains an attestation that its authorization server accepted the agent's grant and exchanges it at the identity provider for an onward grant. The onward grant names the same Agent Principal, and for delegated access the same user, as the agent's grant to the gateway; the gateway is its client, not an additional actor, and the grant lists the gateways on its path in a separate claim. The document extends the Identity Continuation Assertion to self-acting chains rooted in a WAG, and defines the permission a gateway needs to continue an agent's chain and the governance events that end it.¶

1. Introduction

An agent reaches a tool gateway, such as a Model Context Protocol (MCP) gateway reached through [EMA], with an access token obtained under [FEDERATION]. The gateway selects a tool at request time and calls it in another resource domain, whose authorization server does not accept the gateway's token. The gateway holds neither the user's identity assertion nor the agent's credential, and calling the tool as itself would show the tool one client for every agent behind it: the shared-client problem that [FEDERATION] addresses.¶

[ICA] lets a workload continue a request derived from an ID-JAG, through OAuth 2.0 Token Exchange [RFC8693], to another resource authorization server (RAS) that trusts the same identity provider (IdP). Applied to governed agents, a gateway exchanges evidence of an accepted request for a new grant, and the IdP preserves the agent and user, checks that the gateway may continue for that agent, and authorizes access to the next resource.¶

The onward grant names the Agent Principal and acting relationship of the chain's root grant, and for delegated access the same user. The continuing client, typically a gateway, is its client, not an added actor, and a separate claim, continuation_via, discloses the gateways on the path (Section 6.4.1, Section 6.4.2). A downstream RAS and API that implement [FEDERATION], with DPoP at the RAS token endpoint, therefore accept it unchanged (Section 7). This document also adds the Continuation Association, the IdP's permission for a client to continue an agent's chains; extends [ICA] to self-acting chains, anchored to an agent session; and ends chains on governance events. Appendix B lists each change to [ICA] and [FEDERATION].¶

1.1. Protocol Overview

An agent calls a tool gateway, and the gateway calls a tool in another resource domain for the same agent. Inbound, the gateway is the API for the agent's access token; outbound, it is the continuing client at the Continuation Assertion Issuer (CAI), the IdP, and the tool's RAS. Here the gateway's RAS also performs the CAI role.¶

  1. The agent's client obtains a governed grant for the gateway's RAS, which roots a chain where policy permits (Section 3).¶

  2. The client redeems it, and the RAS binds the handle (Section 4).¶

  3. The agent calls the gateway, which applies the API processing of [FEDERATION].¶

  4. The gateway exchanges the access token at the CAI for an assertion (Section 5).¶

  5. The gateway presents the assertion to the IdP, which checks the chain, the gateway's Continuation Association, and the agent's authorization for the tool, and issues an onward grant naming the same agent, with the gateway as client (Section 6).¶

  6. The tool's RAS processes the onward grant as any governed grant (Section 7).¶

Three lifetimes are independent, as in Section 6 of [ICA]: a grant's short redemption window, the access token each RAS issues under its own policy, and the chain that the IdP holds. Ending a chain stops new continuations only. Grants and access tokens already issued, and any refresh token a target issues, keep their own lifetimes (Section 9). Appendix A shows the messages.¶

1.2. Scope

This document applies under these conditions:¶

  • One IdP: Every RAS in a chain trusts the IdP that issued the root grant. Continuity across a chain of IdPs is out of scope.¶

  • One agent: Continuation never changes the Agent Principal. A continuing client is governed as a client, through its Continuation Associations, its attribution as client_id, and its registrations. One that exercises its own authority and needs authorization, attribution, or disablement as a principal is an Agent Principal of its own ("Governance Boundary and Execution Independence" in [FEDERATION]), and its acting for another agent is multi-agent delegation, which [FEDERATION] excludes.¶

  • An accepted grant: The gateway's access token comes from a RAS that redeemed a governed grant. Where the IdP itself issues the gateway's access tokens, there is no hop to continue.¶

Whether a call still serves approved work is outside this document, as in [FEDERATION]. This document defines one claim, continuation_via (Section 6.4.2), and no new token format, error code, or request parameter.¶

2. Conventions and Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [BCP14] (RFC2119) (RFC8174) when, and only when, they appear in all capitals, as shown here.¶

Agent Principal, Identity Binding, Client Association, acting relationship, Delegation Authorization, Agent Authorization, Governance Tenant, Target Tenant, and grant proof key follow [FEDERATION]. Continuation Assertion Issuer (CAI), Identity Continuation Assertion, continuation handle, chain, hop, chain authorization, lifecycle anchor, canonical actor identity, and continuation-aware RAS follow [ICA]. ID-JAG and WAG refer to the grants as [FEDERATION] profiles them.¶

In brief, for readers new to [ICA]: a chain is the IdP's record of grants continued from one root grant; each grant in it is a hop, named by an opaque continuation handle that the grant carries; the RAS that accepts a grant binds its handle to the authorization it creates, and a carrier conveys the handle within that RAS's domain (Section 5.3 of [ICA]). The actor gate is the check, under [FEDERATION], that an agent may act for a user at a resource.¶

[ICA] and [FEDERATION] use some of the same words differently:¶

This document defines these terms:¶

Gateway:

A resource server that receives requests from agents and calls other resources for them, choosing the target at request time.¶

Continuing client:

The OAuth client, identified at each server by its registration there, that obtains an Identity Continuation Assertion, presents it to the IdP, and redeems the onward grant. It is a client in the sense of [FEDERATION]; the chain, not its identity, identifies the agent.¶

Source hop:

The hop whose authorization a continuing client's incoming request carries. A continuing client that cannot see the handle identifies the source hop by the incoming access token or carrier.¶

Governed chain:

A chain rooted in a governed ID-JAG (a delegated chain) or WAG (a self-acting chain) (Section 3.1).¶

Continuation Association:

An approved permission for an authenticated OAuth client to continue an Agent Principal's governed chains in one acting relationship (Section 6.2).¶

Agent session:

IdP state recording that an Agent Principal has recently authenticated through one Identity Binding; the lifecycle anchor of a self-acting chain (Section 3.3).¶

Onward grant:

A governed ID-JAG or WAG issued on a continuation exchange.¶

3. Establishing a Governed Chain

The root exchange is grant issuance under [FEDERATION]. For a governed root, tenant policy permits continuation (Section 5.1.2 of [ICA]) only when both:¶

  • it permits continuation for the Agent Principal and acting relationship; and¶

  • the Delegation Authorization or Agent Authorization under which the root grant is issued permits the agent's access to continue through other clients.¶

When it does, and the root resolves to a lifecycle anchor (one of Section 6.1 of [ICA] for a delegated chain, or the anchor of Section 3.3), the IdP MUST establish a chain under Section 5.1.2 of [ICA]. Otherwise the IdP issues the governed grant without a handle, as [FEDERATION] specifies. As in [ICA], no request parameter requests establishment, and advertised support does not authorize it. The root grant's only addition to [FEDERATION] is the identity_continuation_handle claim (Section 4 of [ICA]).¶

3.1. Governed Chain Authorization

For a governed chain, the IdP records these facts in the chain authorization (Section 5.1.4 of [ICA]), in addition to those ICA requires, and treats them as follows at each continuation:¶

Table 2: Recorded facts of a governed chain
Recorded fact At each continuation
Acting relationship, Agent Principal, Governance Tenant, and root client Fixed; never resolved again
For a delegated chain, the user and authentication context; for a self-acting chain, the agent session Fixed; the user or session remains active (Section 9)
Identity Binding, Client Association, and credential through which the root resolved the agent Each remains enabled, unrevoked, and able to permit the root grant's issuance (Section 9)
Delegation Authorization or Agent Authorization under which the root grant was issued Not withdrawn as a whole; current authorization governs each target and authority (Section 6.3)

The Continuation Association, the Target Tenant, the user's subject at the target, and the continuing client's registration there are evaluated for each onward grant. Current policy can narrow the chain authorization but cannot exceed it (Section 5.1.4 of [ICA]). The limits of Section 6.3 of [ICA], including the actor-lineage depth bound, apply to the IdP's hop records, whose lineage entries are the root client and the continuing clients.¶

The IdP SHOULD also enforce a configured continuation window: it refuses continuation from a hop more than that window after it issued the hop, with invalid_grant as for those limits. The window bounds how long a CAI, including one that a compromised gateway operator controls, can obtain continuations from a hop it accepted. A deployment whose gateway continues from durable task state sets the window to the task's needs.¶

3.2. Delegated Root

The root ID-JAG follows "Delegated Issuance: ID-JAG" in [FEDERATION], and its anchors are those of Section 6.1 of [ICA]. For an ID Token subject, the anchor is the user's IdP session that the ID Token's sid identifies; sid is optional, so an IdP that establishes session-anchored chains includes it in the ID Tokens it issues to agents' clients. The root exchange can use either resolution mode of [FEDERATION], including presented-evidence mode, in which the request carries the agent's workload credential as actor_token; [FEDERATION] processes it ("Agent Resolution Input Validation"), and Section 5.1.1 of [ICA] leaves that processing out of scope.¶

3.3. Self-Acting Root and Agent Session

This section extends [ICA] to chains with no user. The root WAG follows "Self-Acting Issuance: WAG" in [FEDERATION] and carries the root handle, which the IdP generates under rules 1 and 2 of Section 4 of [ICA]. A self-acting chain has no authentication context, so its onward WAGs carry no auth_time, acr, or amr.¶

The lifecycle anchor of a self-acting chain is an agent session, which replaces the user-rooted anchors of Section 6.1 of [ICA]; the prohibition there on rooting a chain from an access token still applies. An agent session is evidence that the Agent Principal recently authenticated through one Identity Binding. It does not show that any particular work continues, and the Agent Authorization, not the session, governs what the chain may do.¶

  • Creation: When a self-acting issuance establishes a chain, the IdP anchors it to the active agent session for the resolved Agent Principal and the Identity Binding it resolved through, creating one if none is active. An ended session is never revived.¶

  • Refresh: Completing steps 1 to 3 of "Self-Acting Issuance: WAG" in [FEDERATION] through that binding refreshes the session: client authentication, agent resolution through the binding, and the self-acting Client Association check, whether or not issuance is then authorized. The IdP MUST NOT refresh it on any other request, including a continuation exchange or delegated issuance.¶

  • Idle timeout: The IdP MUST end an agent session that has not been refreshed within its configured idle timeout.¶

  • Absolute expiration: The IdP MUST set a finite absolute expiration when it creates an agent session, no later than a configured maximum, and MUST NOT extend it.¶

  • Governance events: An event of Section 9 that applies to the session's Agent Principal or Identity Binding also ends the session.¶

A self-acting chain ends with its agent session (Section 6.2 of [ICA]), which neither the gateway nor the CAI can keep active. Work that a gateway performs after the agent stops authenticating, such as queued work, therefore loses continuation at the idle timeout; work that must outlive the agent's authentication needs a durable anchor (Appendix B.4). A working agent obtains a new WAG at least as often as its gateway access token expires, since WAG redemption yields no refresh token, so a deployment sets the idle timeout longer than that token's lifetime. If the token outlives the session, continuation fails and the gateway's response leads the agent's client to a new root grant (Section 8.3). IdP instances evaluate the idle timeout and the absolute expiration against shared session state. An instance that cannot confirm the session's state MUST reject the request rather than issue, as Section 5.5.7 of [ICA] requires for replay reservations, and MUST NOT treat the session as ended on that basis; the chain stays continuable.¶

4. Root Redemption at the Gateway's RAS

The gateway's RAS redeems the root grant under "Grant Redemption at the RAS" in [FEDERATION]. When continuation-aware, it also binds the handle as Section 5.2 of [ICA] specifies, for a WAG as for an ID-JAG, and exposes it to the CAI through a carrier of Section 5.3 of [ICA].¶

A continuation-aware RAS selects access-token protection under "Access-Token Protection" in [FEDERATION], including for a continuation-capable grant that carries cnf. For such a grant, this replaces step 3 of Section 5.2 of [ICA], which permits only a DPoP-bound access token.¶

Whatever the grant's binding, the RAS MUST NOT record an authorization as eligible for continuation when it issued a bearer access token for that authorization, unless resource policy explicitly permits continuation from bearer access tokens for that client and resource. The usual case is an unbound root grant redeemed without a DPoP proof, as governed agent access permits. A hop therefore remains sender-constrained from the RAS to the continuing client unless policy accepts the exposure that Section 9.1 of [ICA] describes.¶

The CAI's attestation establishes that the RAS accepted the hop, not that the gateway authorized the request, which the gateway does as the API under "Access at the Resource Server" in [FEDERATION].¶

5. Assertion Issuance

Section 5.4 of [ICA] applies unchanged to both chain types. The CAI attests acceptance, activity, and the continuing client's association with the authorization, by the RAS's own authorization semantics; it evaluates no governance relationship, and the assertion carries no Agent Principal, user, or acting relationship. The CAI and the IdP are configured with the same canonical actor identity for the continuing client, which the CAI places in the assertion's act and the IdP compares (Section 5.5.2 of [ICA]).¶

6. Continuation Exchange at the IdP

6.1. Request

The continuing client sends the continuation request of Section 5.5.1 of [ICA], with client authentication under Section 5.5.2 of [ICA] and a DPoP proof of the assertion's cnf key. The common parameters and rules of "Token Exchange Request" in [FEDERATION] apply to it, so these parameters are REQUIRED:¶

Table 3: Continuation request parameters
Parameter Value
requested_token_type urn:ietf:params:oauth:token-type:id-jag for a delegated chain; urn:ietf:params:oauth:token-type:wag (provisional) for a self-acting chain
audience One target RAS issuer identifier
resource Exactly one resource URI under [RFC8707], served by the RAS named in audience
scope Non-empty scope string for the requested resource

The continuing client selects requested_token_type by the acting relationship it determined for the received access token as the API ("Profile Applicability" under "Access at the Resource Server" in [FEDERATION]). authorization_details is processed as in [FEDERATION].¶

6.2. Continuation Association

A Continuation Association permits an authenticated client to continue an Agent Principal's governed chains in one acting relationship. It belongs to the Governance Tenant of those chains and does not apply to chains in another. It can restrict targets and authority, and it narrows, without replacing, the restrictions on who may continue that the chain authorization records (Section 5.1.4 of [ICA]). It has these limits:¶

  • A Client Association does not imply a Continuation Association, nor the reverse.¶

  • Permission to continue delegated chains does not imply permission to continue self-acting chains, nor the reverse.¶

  • A Continuation Association is not an Identity Binding. A continuation exchange performs no agent resolution: the onward grant's agent comes only from the chain record, even when the continuing client is also bound to an agent of its own.¶

Policy representation and administration are outside this document.¶

6.3. Validation

For a first presentation of an assertion for a hop of a governed chain, the IdP MUST perform the following steps in order and MUST reject the request at the first step that fails, with the error of Section 6.5. The checks of Section 5.5.3 of [ICA] apply within the steps that cite them, changed only as stated.¶

  1. Client and proof: Authenticate the client, map it to its canonical actor identity (Section 5.5.2 of [ICA]), and validate the DPoP proof.¶

  2. Request parameters (ICA rule 1): The parameters of Section 6.1 replace that rule's requested token type, resource, and scope requirements.¶

  3. Assertion (ICA rules 2 and 3): The assertion is well formed and validly signed by an issuer trusted as CAI for the hop's RAS.¶

  4. Current actor (ICA rule 5): The assertion's act names the authenticated client's canonical actor identity, and the DPoP proof matches its cnf. As Section 5.5.6 of [ICA] requires, these checks precede every chain-state error.¶

  5. Chain state (ICA rule 4): The hop is an accepted hop of an active chain, and neither it nor an ancestor is revoked. The chain has not ended under Section 9, requested_token_type is the chain's grant type, and the chain and hop are within ICA's limits and the continuation window (Section 3.1). An ended chain takes precedence over a wrong type, which takes precedence over a limit.¶

  6. Continuer: A current Continuation Association in the chain's Governance Tenant permits the client for the chain's Agent Principal and acting relationship, and so do the chain authorization's restrictions on who may continue (Section 5.1.4 of [ICA]).¶

  7. Target context (ICA rule 5, replacing its subject resolution): The Target Tenant for the requested resource, the continuing client's registration at the target RAS ("Issuance Prerequisites" in [FEDERATION]), and, for a delegated chain, the user's subject at the target ("Subject Resolution" in [FEDERATION]) each resolve unambiguously. A self-acting chain's subject is its Agent Principal, which is not resolved per target.¶

  8. Freshness and replay (ICA rule 6).¶

  9. Authorization (ICA rule 7): The IdP authorizes the onward grant under "Issuance Authorization" in [FEDERATION] for the chain's Agent Principal and, for a delegated chain, its user, in the root client's context, for the requested target and authority. A current Delegation Authorization or Agent Authorization that permits continuation covers them; it need not name the continuing client. The Continuation Association's restrictions and the chain authorization also bound the target and authority. Withdrawal of the root authorization as a whole is chain state (step 5), not a failure of this step.¶

Because step 6 precedes step 7, a client without a Continuation Association learns nothing about where the chain's user resolves. The rules of [FEDERATION] for agent resolution and subject tokens do not apply to the assertion. The IdP reserves the assertion's (iss, jti) only after every step succeeds, as Section 5.5.7 of [ICA] requires, so a rejected request consumes nothing.¶

An IdP that offers idempotent retry (Section 5.5.7.1 of [ICA]) MUST include requested_token_type in the request fingerprint.¶

A presentation that matches an issued reservation is recovery, not a first presentation. Recovery follows Section 5.5.7.1 of [ICA]: after client authentication, the key proof, and the fingerprint, the IdP returns the grant it issued if that grant is unexpired, neither the hop nor an ancestor is revoked, and the chain has not ended, including under Section 9. No other step of this section applies, so recovery consumes no limit, and a client whose response was lost recovers even the last continuation that a hop-count limit permits.¶

6.4. Onward Grants

The response follows Section 5.5.4 of [ICA], with issued_token_type equal to the requested grant type and no refresh token. Every onward grant carries the common claims of "Common Grant Claims, Lifetime, and Response" in [FEDERATION], a fresh child handle under Section 4 of [ICA], and cnf.jkt for the key proven in the request (Section 5.5.2 of [ICA]). The configured grant lifetime limit of "Common Grant Claims, Lifetime, and Response" in [FEDERATION] applies. The lifetime bounds that [FEDERATION] derives from a subject credential and an agent-resolution input do not apply to continuation, and the assertion's expiration does not cap the onward grant. An onward WAG MUST NOT outlive the absolute expiration of its chain's agent session.¶

6.4.1. Identity Preservation

The IdP MUST construct every onward grant of a governed chain so that:¶

  • it is the chain's grant type: an ID-JAG for a delegated chain and a WAG for a self-acting chain;¶

  • it names the chain's Agent Principal: in an ID-JAG as the single act object, with the IdP issuer as iss and the Agent Principal identifier as sub, and in a WAG as iss and sub, with no act;¶

  • for a delegated chain, it names the chain's user, resolved for the target RAS;¶

  • its client_id identifies the continuing client's registration at the target RAS ("Issuance Prerequisites" in [FEDERATION]); and¶

  • it lists the chain's continuing clients in continuation_via (Section 6.4.2).¶

The continuing client MUST NOT appear in the onward grant's act; it appears as the grant's client and in continuation_via, which disclose it without making it an actor. The IdP takes the Agent Principal, the user, and the acting relationship from its chain record, never from the assertion or the request, so the assertion's act never becomes the governed actor.¶

Continuation never converts the acting relationship. The IdP MUST NOT issue a WAG from a delegated chain or an ID-JAG from a self-acting chain. For a chain established without this document, it MUST NOT issue a governed onward grant, and for a governed chain it MUST NOT issue an onward ID-JAG whose act is constructed under Section 5.5.5 of [ICA]. Appendix C.1 explains the choice.¶

6.4.2. Path Disclosure

Every onward grant of a governed chain discloses the continuing clients it passed through, as intermediaries rather than actors, in this claim:¶

continuation_via:

A JSON array of the canonical actor identities (Section 5.5.2 of [ICA]) of the continuing clients of the hops from the root to the hop being issued, oldest first, so that the last entry is the current continuing client. Each entry is a JSON object with iss and sub string members; a recipient ignores other members. The root client does not appear.¶

The IdP MUST include continuation_via in every onward grant of a governed chain and MUST derive it from its hop records, never from the assertion or the request, following the lineage rules of Section 5.5.5 of [ICA]: parent references are immutable, sibling branches are excluded, and consecutive identical entries merge. The list is complete. Policy that narrows the disclosed depth of act under [ICA] does not narrow it, because a forwarding intermediary is disclosed, never hidden. The last entry and client_id identify the same continuing client, the entry by its canonical actor identity and client_id by its registration at the target.¶

A recipient MUST NOT treat an entry as an actor: entries are not subject to the actor gate and authorize nothing. A target RAS MAY use the list in its policy, for example to admit agents only through approved gateways, and MAY convey it unchanged in the access token or introspection response it issues. A target that ignores it still conforms to [FEDERATION].¶

This document defines continuation_via for governed chains. It is proposed for [ICA] as the disclosure of forwarding intermediaries in general (Appendix B.3). Kerberos and AWS disclose forwarding services in the same way ([KERBEROS-PAC], [AWS-CALLEDVIA]; Appendix C.1).¶

6.4.3. Delegated: ID-JAG

The onward ID-JAG uses the format and claims of Section 3.1 of [ID-JAG] and the following:¶

Table 4: Onward ID-JAG subject, actor, client, and path claims
Claim Value
sub The chain's user, in the IdP's subject namespace for the target RAS
act The object of "Actor Resolution and Construction" in [FEDERATION], with the chain's Agent Principal as sub and the IdP issuer as iss; any sub_profile reflects the IdP's current classification
client_id The continuing client's registration at the target RAS
auth_time, acr, amr Copied unchanged from the root, as Section 5.5.5 of [ICA] requires
continuation_via The chain's continuing clients (Section 6.4.2)

Section 5.5.5 of [ICA] applies to the onward ID-JAG and to the IdP's hop records, including immutable parent references, ancestry that excludes sibling branches, and the merging of consecutive identical actors that the actor-lineage depth bound counts. 7. Onward Redemption and Access

The continuing client redeems the onward grant under "Redemption Request" in [FEDERATION]: the urn:ietf:params:oauth:grant-type:jwt-bearer grant type, client authentication as the client the grant names, and a DPoP proof of the grant's cnf key. For governed chains, this replaces the jwt-dpop redemption of Section 5.5.5 of [ICA]; Section 4.4 of [ID-JAG] requires jwt-bearer, and [FEDERATION] applies the grant confirmation checks of ID-JAG to it. Every onward grant carries cnf, so the target RAS needs DPoP support at its token endpoint ("Grant Protection" in [FEDERATION]), which the continuing client verifies under "Capability Discovery" in [FEDERATION].¶

The target RAS and API process the onward grant and the resulting access token as for any governed grant ("Grant Redemption at the RAS" and "Access at the Resource Server" in [FEDERATION]). They see the same Agent Principal, and for delegated access the same user and actor gate, as for the agent's own client; only client_id and continuation_via name continuing clients, and resource policy can permit or deny an agent's access through a particular client or path. A RAS that does not implement [ICA] ignores the handle. One that does binds it and applies Section 4, so that a gateway in its domain can continue the chain as a further hop that again names the same agent.¶

8.3. Continuing a Request

To continue a request, a gateway:¶

  1. processes the incoming access token as the API ("Access at the Resource Server" in [FEDERATION]), including the actor gate;¶

  2. obtains an assertion from the CAI with that request's own token, as below (Appendix A.2 shows the request);¶

  3. verifies the target's capabilities and requests the chain's grant type from the IdP (Section 6.1, Appendix A.3);¶

  4. redeems the onward grant with jwt-bearer and a proof of its key (Section 7);¶

  5. reuses downstream tokens only within the same context and source hop; and¶

  6. handles errors without falling back, as below.¶

The CAI binds the assertion to the handle of the token the gateway presents (Section 5.4.3 of [ICA]), but a gateway that holds several agents' tokens chooses which to present. The gateway MUST therefore request an assertion only with the access token, or a carrier derived from it, of the request it is continuing.¶

"Client Token Reuse" in [FEDERATION] applies to every onward grant and downstream access token the gateway holds: it reuses one only for a request in the same agent, user, tenant, target, authority, and proof context. The gateway MUST also reuse one only for a request that arrived on the same source hop. Two chains can share all of that context yet differ in root binding, credential, anchor, and revocation, so serving one chain's request with a token obtained on another would let it continue after its own chain had ended (Section 8 of [ICA]). Each source hop therefore needs its own continuation, once for each target.¶

When continuation from a request's source hop fails with invalid_continuation, or with a limit failure other than a rate limit, the gateway SHOULD reject the agent's request with HTTP 401 and the invalid_token error code of the access token's scheme ([RFC6750], [RFC9449]), so that the agent's client obtains a new access token and, with it, a new root grant.¶

After the IdP rejects a governed continuation for a request, the continuing client MUST NOT serve that request with its own authority or through a chain established without this document. This extends the no-fallback rule of "Profile Applicability and Downgrade Prevention" in [FEDERATION], which covers retrying as ordinary access or without proof. Gateway-side tool filtering narrows what the gateway attempts but does not authorize.¶

10. Conformance and Capability Advertisement

10.1. Conformance Claims

The roles are the IdP, the continuation-aware RAS and its CAI, the continuing client, and the target RAS. An implementation claims delegated continuation, self-acting continuation, or both, for each role it implements. Each claim requires the same realization under [FEDERATION] and the applicable requirements of [ICA] as this document changes them. A target RAS that does not continue the chain implements [FEDERATION] with DPoP support at its token endpoint, and nothing from this document.¶

Each claim has this mandatory interoperability path:¶

  • Client authentication: The continuing client, CAI, IdP, and target RAS MUST implement [RFC7523] private_key_jwt client authentication, under "Dedicated Client Identity" in [FEDERATION] for its audience, replay, and retry rules.¶

  • Proof: They MUST implement DPoP [RFC9449] with the algorithms of "Client Authentication and Algorithms" in [FEDERATION].¶

  • Assertion issuance: Every CAI that serves a continuing client MUST support assertion issuance at its token endpoint with an access-token subject_token (Section 5.4.1 of [ICA]), resolving the token as Section 5.4.6 of [ICA] describes when the CAI is not the accepting RAS. The continuing client MUST implement that request.¶

10.2. Metadata

A continuation-aware RAS that binds handles of governed grants lists urn:ietf:params:oauth:grant-profile:governed-agent-continuation in authorization_grant_profiles_supported (Section 7.2 of [ID-JAG]), together with the governed profile URIs that identify the grants it accepts. The value indicates handle binding under Section 5.2 of [ICA] with the access-token protection and eligibility of Section 4, and redemption of onward grants with jwt-bearer (Section 7); it does not indicate jwt-dpop support. A RAS lists ICA's urn:ietf:params:oauth:grant-profile:id-jag-continuation, with the requirements of Section 7.2 of [ICA], only if it also binds handles of chains established without this document. As for the self-acting profile URIs of [FEDERATION], use of this parameter for WAGs awaits coordination (Appendix B.3).¶

An IdP that supports delegated continuation advertises identity_continuation_supported (Section 7.1 of [ICA]), which indicates continuation-capable ID-JAG issuance; an IdP that supports only self-acting continuation does not. Support for self-acting continuation is established through trusted configuration ("Capability Discovery" in [FEDERATION]); no IdP metadata advertises it. Advertisement indicates capability and does not authorize continuation.¶

11. Security Considerations

The security considerations of [ICA] and [FEDERATION] apply.¶

11.1. Gateway Compromise

A compromised gateway that can still authenticate and prove its key can continue each chain whose access token it has received, to any target that the chain authorization, the agent's current authorization, and its Continuation Associations permit, and can use the downstream tokens it holds until they expire. Where its operator does not control the CAI, it cannot continue a chain whose token it has not received, because the CAI attests only hops bound to tokens presented to it (Section 5.4.3 of [ICA]). In the baseline topology the operator runs the CAI, which can attest any hop its RAS accepted, as Section 9.5 of [ICA] notes for a compromised RAS, until the chain ends or the hop's continuation window passes. In either case it cannot change the agent or user, convert the acting relationship, or exceed the agent's own authorization. Narrow Continuation Associations, chain authorizations that restrict targets, a short continuation window, short downstream token lifetimes, and sender-constrained ingress reduce the exposure; the last also keeps a stolen bearer token at the gateway from inducing an honest continuation (Section 9.1 of [ICA], Section 4).¶

11.2. Attribution Through an Intermediary

Downstream records attribute an action to the Agent Principal and, for delegated access, the user, with the continuing client as client_id and every continuing client on the path in continuation_via. A target can therefore audit and authorize the path without consulting the IdP, whose hop records remain authoritative. A handle does not distinguish a root grant from an onward grant; a resource that must tell a gateway from the agent's own client uses the authenticated client_id or the presence of continuation_via, which only onward grants carry.¶

11.3. Self-Acting Chains

When an agent stops authenticating through a binding, its self-acting chains through that binding end within the idle timeout without administrative action. A party holding the agent's credential can keep its session active, as a stolen user credential can keep a user session active, until the absolute expiration or the credential's revocation (Section 9).¶

11.4. Disablement Windows

Issued onward grants and downstream access tokens, including those a gateway has cached, remain usable after a chain ends until they expire or their revocation is applied. A refresh token that a target RAS issues under "Optional RAS Refresh Tokens" in [FEDERATION] extends access further; a deployment that relies on chain ending configures its targets not to issue refresh tokens to continuing clients, so that renewal is another continuation.¶

12. Privacy Considerations

The privacy considerations of [ICA] and [FEDERATION] apply. Continuation discloses the Agent Principal identifier to each target the gateway reaches, extending the cross-resource correlation that a stable agent identifier allows, and the gateway learns which agents and users call which tools. An onward grant discloses every continuing client on the path, as Section 5.5.5 of [ICA] would, but as intermediaries rather than actors, and it does not disclose the root client. The IdP's hop records hold the complete path and are sensitive audit data.¶

Appendix C. Design Rationale

This non-normative appendix records the principal design choices.¶

C.1. The Gateway Is a Client, Not an Actor

In [FEDERATION], the Agent Principal is the authorization identity, and client and workload identities do not replace it downstream. A gateway that continues an agent's request selects the target but exercises the agent's authority, within the agent's authorization and under the Continuation Association, a permission of the same kind as a Client Association. A gateway governed as a client has its own permission, attribution as client_id, and registrations that can be disabled, without becoming a principal. A gateway that exercises its own authority and needs authorization, attribution, or disablement as a principal is an Agent Principal, and its acting for another agent is delegation between agents, outside [FEDERATION].¶

Placing the gateway in act, as Section 5.5.5 of [ICA] does for the current actor, would give every agent behind a gateway the same outermost actor, recreating at the actor level the shared-client problem. A governed RAS and API would have to process nested act, which [FEDERATION] rejects, and a WAG, which carries no act, could not represent the gateway at all.¶

In the terms of [WS-TRUST], the gateway requests access on behalf of the agent rather than acting as it: the agent acts for the user, and the gateway forwards. A forwarding intermediary is still disclosed, in continuation_via, as Kerberos records the services a delegated ticket passed through ([KERBEROS-PAC]) and AWS records the services that made a request on a principal's behalf ([AWS-CALLEDVIA]). Attribution and path-based policy therefore need no lineage in act.¶

The user's approval reaches the gateway through the Delegation Authorization, which must permit continuation for a delegated chain to exist. Continuation never turns a delegated chain into a WAG, which would let an agent act on its own authority because a user's request reached it.¶

C.2. Governance Events End the Chain

The root's Identity Binding, Client Association, and credential are the chain's only link between the agent and an authenticated client. When any is withdrawn, the chain has no current basis, even if another binding resolves the same agent for new issuance. An ended chain stays ended, as in Section 6.2 of [ICA], and reactivation permits new decisions only, as in [FEDERATION].¶

C.3. Self-Acting Chains Anchor to an Agent Session

[ICA] anchors a chain to state showing that its principal is still present and records what the chain may do separately. An Agent Authorization is often indefinite, so as an anchor it cannot tell a working agent from one that has stopped; a dedicated-client assertion lasts one request, and routine credential rotation would end chains. Only the agent's own authentication refreshes an agent session, so a gateway cannot extend a chain it continues, and keeping it per Identity Binding stops activity on one platform from sustaining chains rooted through another. The absolute expiration bounds a session the agent keeps active, as the absolute authorization expiration of "Optional RAS Refresh Tokens" in [FEDERATION] bounds refresh; without it, a chain would substitute for the refresh token that [WAG] prohibits.¶
