      Identity Continuation Profile for Governed Agent Federation
       draft-mcguinness-oauth-governed-agent-continuation-latest

Abstract

   The OAuth 2.0 Profile for Governed Agent Federation carries a
   governed Agent Principal from an identity provider into one resource
   domain, as the actor of an Identity Assertion JWT Authorization Grant
   (ID-JAG) or the subject of a Workload Authorization Grant (WAG).  A
   gateway that receives such an agent's request and calls resources in
   other domains for it holds neither the user's credential nor the
   agent's.

   This document profiles the Identity Continuation Assertion for
   governed agents, with gateways as the primary deployment.  The
   gateway obtains an attestation that its authorization server accepted
   the agent's grant and exchanges it at the identity provider for an
   onward grant.  The onward grant names the same Agent Principal, and
   for delegated access the same user, as the agent's grant to the
   gateway; the gateway is its client, not an additional actor, and the
   grant lists the gateways on its path in a separate claim.  The
   document extends the Identity Continuation Assertion to self-acting
   chains rooted in a WAG, and defines the permission a gateway needs to
   continue an agent's chain and the governance events that end it.

1.  Introduction

   An agent reaches a tool gateway, such as a Model Context Protocol
   (MCP) gateway reached through [EMA], with an access token obtained
   under [FEDERATION].  The gateway selects a tool at request time and
   calls it in another resource domain, whose authorization server does
   not accept the gateway's token.  The gateway holds neither the user's
   identity assertion nor the agent's credential, and calling the tool
   as itself would show the tool one client for every agent behind it:
   the shared-client problem that [FEDERATION] addresses.

   [ICA] lets a workload continue a request derived from an ID-JAG,
   through OAuth 2.0 Token Exchange [RFC8693], to another resource
   authorization server (RAS) that trusts the same identity provider
   (IdP).  Applied to governed agents, a gateway exchanges evidence of
   an accepted request for a new grant, and the IdP preserves the agent
   and user, checks that the gateway may continue for that agent, and
   authorizes access to the next resource.  The agent's own client can
   continue a chain in the same way, as for scheduled work after the
   user signs out (Appendix A.7).

   OAuth Identity and Authorization Chaining Across Domains
   [ID-CHAINING] offers another route: an authorization server in the
   gateway's domain issues a JWT authorization grant that the next
   domain's authorization server accepts.  In that topology, each target
   trusts the gateway-domain authorization servers whose grants it
   accepts, and Identity Chaining does not require consulting the
   governing IdP at each hop.  This profile does: continuation returns
   to the IdP, which the target already trusts for governed grants and
   which applies the agent's current authorization and governance state
   at each hop.  The gateway's domain contributes the CAI's attestation
   that its RAS accepted the originating grant, that the resulting
   authorization remains active and eligible for continuation, and that
   the continuing client is associated with it (Section 5.4 of [ICA]).

   The onward grant names the Agent Principal and acting relationship of
   the chain's root grant, and for delegated access the same user.  The
   continuing client, typically a gateway, is its client, not an added
   actor, and a separate claim, continuation_via, discloses the gateways
   on the path (Section 6.5.1, Section 6.5.2).  A downstream RAS and API
   that implement [FEDERATION], with DPoP at the RAS token endpoint,
   therefore accept it unchanged (Section 7).  This document also adds
   the Continuation Association, the IdP's permission for a client to
   continue an agent's chains; extends [ICA] to self-acting chains,
   anchored to an agent session; and ends chains on governance events.
   Appendix B lists each change to [ICA] and [FEDERATION].

1.1.  Protocol Overview

   An agent calls a tool gateway, and the gateway calls a tool in
   another resource domain for the same agent.  Inbound, the gateway is
   the API for the agent's access token; outbound, it is the continuing
   client at the Continuation Assertion Issuer (CAI), the IdP, and the
   tool's RAS.  Here the gateway's RAS also performs the CAI role.

   Agent        IdP       GatewayRAS/CAI     Gateway        ToolRAS
     |           |               |              |               |
     | (1) governed grant with handle H0        |               |
     |---------->|               |              |               |
     |<----------|               |              |               |
     | (2) redeem; RAS binds H0  |              |               |
     |-------------------------->|              |               |
     |<--------------------------|              |               |
     | (3) call with access token               |               |
     |----------------------------------------->|               |
     |           |               | (4) assertion for H0         |
     |           |               |<-------------|               |
     |           |               |------------->|               |
     |           | (5) onward grant: same agent, gateway as client
     |           |<-----------------------------|               |
     |           |----------------------------->|               |
     |           |               |              | (6) redeem    |
     |           |               |              |-------------->|
     |           |               |              |<--------------|

           Figure 1: One governed continuation through a gateway

   1.  The agent's client obtains a governed grant for the gateway's
       RAS, which roots a chain where policy permits (Section 3).

   2.  The client redeems it, and the RAS binds the handle (Section 4).

   3.  The agent calls the gateway, which applies the API processing of
       [FEDERATION].

   4.  The gateway exchanges the access token at the CAI for an
       assertion (Section 5).

   5.  The gateway presents the assertion to the IdP, which checks the
       chain, the gateway's Continuation Association, and the agent's
       authorization for the tool, and issues an onward grant naming the
       same agent, with the gateway as client (Section 6).

   6.  The tool's RAS processes the onward grant as any governed grant
       (Section 7).

   Three lifetimes are independent, as in Section 6 of [ICA]: a grant's
   short redemption window, the access token each RAS issues under its
   own policy, and the chain that the IdP holds.  Ending a chain stops
   new continuations only.  Grants and access tokens already issued, and
   any refresh token a target issues, keep their own lifetimes
   (Section 9).  Appendix A shows the messages.

1.2.  Scope

   This document applies under these conditions:

   *  *One IdP:* Every RAS in a chain trusts the IdP that issued the
      root grant.  Continuity across a chain of IdPs is out of scope.

   *  *One agent:* Continuation never changes the Agent Principal.  A
      continuing client is governed as a client, through its
      Continuation Associations, its attribution as client_id, and its
      registrations.  One that exercises its own authority and needs
      authorization, attribution, or disablement as a principal is an
      Agent Principal of its own ("Governance Boundary and Execution
      Independence" in [FEDERATION]), and its acting for another agent
      is multi-agent delegation, which [FEDERATION] excludes.

   *  *An accepted grant:* The gateway's access token comes from a RAS
      that redeemed a governed grant.  Where the IdP itself issues the
      gateway's access tokens, there is no hop to continue.

   Whether a call still serves approved work is outside this document,
   as in [FEDERATION].  This document defines one claim,
   continuation_via (Section 6.5.2), and no new token format, error
   code, or request parameter.

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   [BCP14] (RFC2119) (RFC8174) when, and only when, they appear in all
   capitals, as shown here.

   Agent Principal, Identity Binding, Client Association, acting
   relationship, Delegation Authorization, Agent Authorization,
   Governance Tenant, Target Tenant, and grant proof key follow
   [FEDERATION].  Continuation Assertion Issuer (CAI), Identity
   Continuation Assertion, continuation handle, chain, hop, chain
   authorization, lifecycle anchor, canonical actor identity, and
   continuation-aware RAS follow [ICA].  ID-JAG and WAG refer to the
   grants as [FEDERATION] profiles them.

   In brief, for readers new to [ICA]: a chain is the IdP's record of
   grants continued from one root grant; each grant in it is a hop,
   named by an opaque continuation handle that the grant carries; the
   RAS that accepts a grant binds its handle to the authorization it
   creates, and a carrier conveys the handle within that RAS's domain
   (Section 5.3 of [ICA]).  The actor gate is the check, under
   [FEDERATION], that an agent may act for a user at a resource.

   [ICA] and [FEDERATION] use some of the same words differently:

   Unqualified, "actor" means the Agent Principal in an ID-JAG's act,
   and "workload" keeps its meaning in [FEDERATION].  A continuing
   client has a canonical actor identity under [ICA] only so that the
   IdP can match the assertion's act to the authenticated client.

   This document defines these terms:

   Gateway:  A resource server that receives requests from agents and
      calls other resources for them, choosing the target at request
      time.

   Continuing client:  The OAuth client, identified at each server by
      its registration there, that obtains an Identity Continuation
      Assertion, presents it to the IdP, and redeems the onward grant.
      It is a client in the sense of [FEDERATION]; the chain, not its
      identity, identifies the agent.

   Source hop:  The hop whose authorization a continuing client's
      incoming request carries.  A continuing client that cannot see the
      handle identifies the source hop by the incoming access token or
      carrier.

   Governed chain:  A chain rooted in a governed ID-JAG (a delegated
      chain) or WAG (a self-acting chain) (Section 3.1).

   Continuation Association:  An approved permission for an
      authenticated OAuth client to continue an Agent Principal's
      governed chains in one acting relationship (Section 6.2).

   Agent session:  IdP state recording that an Agent Principal has
      recently authenticated through one Identity Binding; the lifecycle
      anchor of a self-acting chain (Section 3.3).

   Onward grant:  A governed ID-JAG or WAG issued on a continuation
      exchange.

3.  Establishing a Governed Chain

   The root exchange is grant issuance under [FEDERATION].  For a
   governed root, tenant policy permits continuation (Section 5.1.2 of
   [ICA]) only when both:

   *  it permits continuation for the Agent Principal and acting
      relationship; and

   *  the Delegation Authorization or Agent Authorization under which
      the root grant is issued permits the agent's access to continue
      through other clients.

   When it does, and the root resolves to a lifecycle anchor (one of
   Section 6.1 of [ICA] for a delegated chain, or the anchor of
   Section 3.3), the IdP MUST establish a chain under Section 5.1.2 of
   [ICA].  Otherwise the IdP issues the governed grant without a handle,
   as [FEDERATION] specifies.  As in [ICA], no request parameter
   requests establishment, and advertised support does not authorize it.
   The root grant's only addition to [FEDERATION] is the
   identity_continuation_handle claim (Section 4 of [ICA]).

3.1.  Governed Chain Authorization

   For a governed chain, the IdP records these facts in the chain
   authorization (Section 5.1.4 of [ICA]), in addition to those ICA
   requires, and treats them as follows at each continuation:

    +=====================================+===========================+
    | Recorded fact                       | At each continuation      |
    +=====================================+===========================+
    | Acting relationship, Agent          | Fixed; never resolved     |
    | Principal, Governance Tenant, and   | again                     |
    | root client                         |                           |
    +-------------------------------------+---------------------------+
    | For a delegated chain, the user and | Fixed; the user or        |
    | authentication context; for a self- | session remains active    |
    | acting chain, the agent session     | (Section 9)               |
    +-------------------------------------+---------------------------+
    | Identity Binding, Client            | Each remains enabled,     |
    | Association, and credential through | unrevoked, and able to    |
    | which the root resolved the agent   | permit the root grant's   |
    |                                     | issuance (Section 9)      |
    +-------------------------------------+---------------------------+
    | Delegation Authorization or Agent   | Not withdrawn as a whole; |
    | Authorization under which the root  | current authorization     |
    | grant was issued                    | governs each target and   |
    |                                     | authority (Section 6.4)   |
    +-------------------------------------+---------------------------+

                Table 2: Recorded facts of a governed chain

   The Continuation Association, the Target Tenant, the user's subject
   at the target, and the continuing client's registration there are
   evaluated for each onward grant.  Current policy can narrow the chain
   authorization but cannot exceed it (Section 5.1.4 of [ICA]).  The
   limits of Section 6.3 of [ICA], including the actor-lineage depth
   bound, apply to the IdP's hop records, whose lineage entries are the
   root client and the continuing clients.

   The IdP MUST also enforce a finite continuation window, whose length
   is configured: it refuses a continuation request received after the
   hop's deadline, with invalid_grant as for those limits.  A hop's
   deadline is the time the IdP issued the hop plus the window
   configured then.  Shortening the window can bring existing deadlines
   forward; lengthening it applies only to hops issued afterwards.  The
   deadline limits when a continuation can be requested, not when its
   onward grant issues, so an onward grant whose issuance is deferred
   after a timely request can issue after it.  The window bounds how
   long a CAI, including one that a compromised gateway operator
   controls, can obtain continuations from a hop it accepted.  It does
   not bound the chain: each continuation creates a hop with a deadline
   of its own, and the hop-count limit of Section 6.3 of [ICA] bounds
   how far a chain extends (Section 12.1, Section 11.1).

3.2.  Delegated Root

   The root ID-JAG follows "Delegated Issuance: ID-JAG" in [FEDERATION],
   and its anchors are those of Section 6.1 of [ICA].  For an ID Token
   subject, the anchor is the user's IdP session that the ID Token's sid
   identifies; sid is optional, so an IdP that establishes session-
   anchored chains includes it in the ID Tokens it issues to agents'
   clients.  The root exchange can use either resolution mode of
   [FEDERATION], including presented-evidence mode, in which the request
   carries the agent's workload credential as actor_token; [FEDERATION]
   processes it ("Agent Resolution Input Validation"), and Section 5.1.1
   of [ICA] leaves that processing out of scope.

3.3.  Self-Acting Root and Agent Session

   This section extends [ICA] to chains with no user.  The root WAG
   follows "Self-Acting Issuance: WAG" in [FEDERATION] and carries the
   root handle, which the IdP generates under rules 1 and 2 of Section 4
   of [ICA].  A self-acting chain has no authentication context, so its
   onward WAGs carry no auth_time, acr, or amr.

   The lifecycle anchor of a self-acting chain is an agent session,
   which replaces the user-rooted anchors of Section 6.1 of [ICA]; the
   prohibition there on rooting a chain from an access token still
   applies.  An agent session is evidence that the Agent Principal
   recently authenticated through one Identity Binding.  It does not
   show that any particular work continues, and the Agent Authorization,
   not the session, governs what the chain may do.

   *  *Creation:* When a self-acting issuance establishes a chain, the
      IdP anchors it to the active agent session for the resolved Agent
      Principal and the Identity Binding it resolved through, creating
      one if none is active.  An ended session is never revived.

   *  *Refresh:* Completing steps 1 to 3 of "Self-Acting Issuance: WAG"
      in [FEDERATION] through that binding refreshes the session: client
      authentication, agent resolution through the binding, and the
      self-acting Client Association check, whether or not issuance is
      then authorized.  The IdP MUST NOT refresh it on any other
      request, including a continuation exchange or delegated issuance.

   *  *Idle timeout:* The IdP MUST end an agent session that has not
      been refreshed within its configured idle timeout.

   *  *Absolute expiration:* The IdP MUST set a finite absolute
      expiration when it creates an agent session, no later than a
      configured maximum, and MUST NOT extend it.

   *  *Governance events:* An event of Section 9 that applies to the
      session's Agent Principal or Identity Binding also ends the
      session.

   A self-acting chain ends with its agent session (Section 6.2 of
   [ICA]), which neither the gateway nor the CAI can keep active
   (Section 11.1).  IdP instances evaluate the idle timeout and the
   absolute expiration against shared session state; an instance that
   cannot confirm it refuses temporarily (Section 6.6).

4.  Root Redemption at the Gateway's RAS

   The gateway's RAS redeems the root grant under "Grant Redemption at
   the RAS" in [FEDERATION].  When continuation-aware, it also binds the
   handle as Section 5.2 of [ICA] specifies, for a WAG as for an ID-JAG,
   and exposes it to the CAI through a carrier of Section 5.3 of [ICA].

   A continuation-aware RAS selects access-token protection under
   "Access-Token Protection" in [FEDERATION], including for a
   continuation-capable grant that carries cnf.  For such a grant, this
   replaces step 3 of Section 5.2 of [ICA], which permits only a DPoP-
   bound access token.

   Whatever the grant's binding, the RAS MUST NOT record an
   authorization as eligible for continuation when it issued a bearer
   access token for that authorization, unless resource policy
   explicitly permits continuation from bearer access tokens for that
   client and resource.  The usual case is an unbound root grant
   redeemed without a DPoP proof, as governed agent access permits.  A
   hop therefore remains sender-constrained from the RAS to the
   continuing client unless policy accepts the exposure that Section 9.1
   of [ICA] describes.  An authorization from a deferred redemption is
   not eligible under any policy ("Refresh and Continuation" in
   [OVERSIGHT]).

   The CAI's attestation establishes that the RAS accepted the hop, not
   that the gateway authorized the request, which the gateway does as
   the API under "Access at the Resource Server" in [FEDERATION].

5.  Assertion Issuance

   Section 5.4 of [ICA] applies unchanged to both chain types.  The CAI
   attests acceptance, activity, and the continuing client's association
   with the authorization, by the RAS's own authorization semantics; it
   evaluates no governance relationship, and the assertion carries no
   Agent Principal, user, or acting relationship.  The CAI and the IdP
   are configured with the same canonical actor identity for the
   continuing client, which the CAI places in the assertion's act and
   the IdP compares (Section 5.5.2 of [ICA]).

6.  Continuation Exchange at the IdP

6.1.  Request

   The continuing client sends the continuation request of Section 5.5.1
   of [ICA], with client authentication under Section 5.5.2 of [ICA] and
   a DPoP proof of the assertion's cnf key.  The common parameters and
   rules of "Token Exchange Request" in [FEDERATION] apply to it, so
   these parameters are REQUIRED:

    +======================+=========================================+
    | Parameter            | Value                                   |
    +======================+=========================================+
    | requested_token_type | urn:ietf:params:oauth:token-type:id-jag |
    |                      | for a delegated chain;                  |
    |                      | urn:ietf:params:oauth:token-type:wag    |
    |                      | (provisional) for a self-acting chain   |
    +----------------------+-----------------------------------------+
    | audience             | One target RAS issuer identifier        |
    +----------------------+-----------------------------------------+
    | resource             | Exactly one resource URI under          |
    |                      | [RFC8707], served by the RAS named in   |
    |                      | audience                                |
    +----------------------+-----------------------------------------+
    | scope                | Non-empty scope string for the          |
    |                      | requested resource                      |
    +----------------------+-----------------------------------------+

                 Table 3: Continuation request parameters

   The continuing client selects requested_token_type by the acting
   relationship it determined for the received access token as the API
   ("Profile Applicability" under "Access at the Resource Server" in
   [FEDERATION]). authorization_details is processed as in [FEDERATION].

6.2.  Continuation Association

   A Continuation Association permits an authenticated client to
   continue an Agent Principal's governed chains in one acting
   relationship.  It belongs to the Governance Tenant of those chains
   and does not apply to chains in another.  It can restrict targets and
   authority (Section 6.3), and it narrows, without replacing, the
   restrictions on who may continue that the chain authorization records
   (Section 5.1.4 of [ICA]).  It has these limits:

   *  A Client Association does not imply a Continuation Association,
      nor the reverse.

   *  Permission to continue delegated chains does not imply permission
      to continue self-acting chains, nor the reverse.

   *  A Continuation Association is not an Identity Binding.  A
      continuation exchange performs no agent resolution: the onward
      grant's agent comes only from the chain record, even when the
      continuing client is also bound to an agent of its own.

   Policy representation and administration are outside this document.

6.3.  Restrictions

   A chain authorization's restrictions (Section 5.1.4 of [ICA]) and a
   Continuation Association's restrictions have the meaning this section
   defines; their representation is outside this document.  Either can
   contain these members:

     +============+=================================================+
     | Member     | Content                                         |
     +============+=================================================+
     | Targets    | Target entries, each naming a target RAS issuer |
     |            | and either one resource or one Target Tenant    |
     +------------+-------------------------------------------------+
     | Authority  | Authority entries, each for one target entry: a |
     |            | set of scope values, authorization details      |
     |            | [RFC9396], or both, in that target's vocabulary |
     +------------+-------------------------------------------------+
     | Continuing | Canonical actor identities (Section 5.5.2 of    |
     | clients    | [ICA]); in a chain authorization only, since a  |
     |            | Continuation Association names its client       |
     +------------+-------------------------------------------------+

                    Table 4: Members of a restriction

   The IdP MUST evaluate each restriction as follows:

   *  *Absent:* An absent member restricts nothing, and the other bounds
      of this section still apply.  Where a chain authorization records
      no Targets member, a target that current policy comes to permit is
      reachable from every such chain, as Section 9.2 of [ICA]
      describes.  Likewise, a target that matches no authority entry has
      no authority limited by that restriction.  Absence never removes
      the finite hop-count limit of Section 6.3 of [ICA] or the
      continuation window (Section 3.1).

   *  *Present:* A member present in a chain authorization is fixed for
      the chain's lifetime (Section 5.1.4 of [ICA]).  Current policy can
      narrow access beneath it but cannot exceed it.  A Continuation
      Association's members are current policy and apply as they stand
      at each continuation.

   *  *Empty:* A present member that is empty permits nothing: an empty
      Targets member permits no continuation, an empty Continuing
      clients member permits no client, and an authority entry whose
      scope set or authorization details are present but empty permits
      no access to its target.

   *  *Matching:* A request matches a target entry when its audience
      equals the entry's RAS issuer and, for an entry naming a resource,
      its resource equals that resource or, for an entry naming a Target
      Tenant, the Target Tenant resolved for it in step 7 of Section 6.4
      equals that tenant.  A continuing client matches when its
      canonical actor identity equals a recorded one.  This document
      compares each value as an exact string, without normalization.

   *  *Authority:* A request is within a restriction's authority only if
      it is within every authority entry whose target entry it matches:
      each requested scope value is in the entry's scope set, if the
      entry has one; and, if the entry has authorization details, the
      request carries a non-empty authorization_details array, each of
      whose details is within a recorded detail of the same type under
      that type's rules.  A request without authorization details, or
      with an empty array, is not within such an entry, even when its
      scope is, since its grant would carry the scope without the limit
      the details express.

   *  *Unevaluable:* If the IdP cannot determine that requested
      authorization details are within an authority entry, for example
      because it does not implement their type's comparison, the request
      is not within it.

   *  *Combined:* The chain authorization's restrictions, the
      Continuation Association's restrictions, and the agent's current
      authorization each bound the onward grant independently.  The
      target RAS then applies its own policy.

   The IdP derives a chain authorization's restrictions when it
   establishes the chain, from tenant policy and from the Delegation or
   Agent Authorization under which the root grant is issued.

6.4.  Validation

   For a first presentation of an assertion for a hop of a governed
   chain, the IdP MUST perform the following steps in order and MUST
   reject the request at the first step that fails, with the error of
   Section 6.6.  The checks of Section 5.5.3 of [ICA] apply within the
   steps that cite them, changed only as stated.

   1.  *Client and proof:* Authenticate the client, map it to its
       canonical actor identity (Section 5.5.2 of [ICA]), and validate
       the DPoP proof.

   2.  *Request parameters (ICA rule 1):* The parameters of Section 6.1
       replace that rule's requested token type, resource, and scope
       requirements.

   3.  *Assertion (ICA rules 2 and 3):* The assertion is well formed and
       validly signed by an issuer trusted as CAI for the hop's RAS.

   4.  *Current actor (ICA rule 5):* The assertion's act names the
       authenticated client's canonical actor identity, and the DPoP
       proof matches its cnf.  As Section 5.5.6 of [ICA] requires, these
       checks precede every chain-state error.

   5.  *Chain state (ICA rule 4):* The hop is an accepted hop of an
       active chain, and neither it nor an ancestor is revoked.  The
       chain has not ended under Section 9, requested_token_type is the
       chain's grant type, and the chain and hop are within ICA's limits
       and the continuation window (Section 3.1).  An ended chain takes
       precedence over a wrong type, which takes precedence over a
       limit.

   6.  *Continuer:* A current Continuation Association in the chain's
       Governance Tenant permits the client for the chain's Agent
       Principal and acting relationship, and so do the chain
       authorization's restrictions on who may continue (Section 6.3).

   7.  *Target context (ICA rule 5, replacing its subject resolution):*
       The Target Tenant for the requested resource, the continuing
       client's registration at the target RAS ("Issuance Prerequisites"
       in [FEDERATION]), and, for a delegated chain, the user's subject
       at the target ("Subject Resolution" in [FEDERATION]) each resolve
       unambiguously.  A self-acting chain's subject is its Agent
       Principal, which is not resolved per target.  Where policy
       requires path disclosure, the target RAS supports it
       (Section 6.5.2).

   8.  *Freshness and replay (ICA rule 6).*

   9.  *Authorization (ICA rule 7):* The IdP authorizes the onward grant
       under "Issuance Authorization" in [FEDERATION] for the chain's
       Agent Principal and, for a delegated chain, its user, in the root
       client's context, for the requested target and authority.  A
       current Delegation Authorization or Agent Authorization that
       permits continuation covers them; it need not name the continuing
       client.  The restrictions of the chain authorization and the
       Continuation Association also bound the target and authority
       (Section 6.3).  Withdrawal of the root authorization as a whole
       is chain state (step 5), not a failure of this step.

   Because step 6 precedes step 7, a client without a Continuation
   Association learns nothing about where the chain's user resolves.
   The rules of [FEDERATION] for agent resolution and subject tokens do
   not apply to the assertion.  The IdP reserves the assertion's (iss,
   jti) only after every step succeeds, as Section 5.5.7 of [ICA]
   requires, so a rejected request consumes nothing.

   An IdP that offers idempotent retry (Section 5.5.7.1 of [ICA]) MUST
   include requested_token_type in the request fingerprint.

   A presentation that matches an issued reservation is recovery, not a
   first presentation.  Recovery follows Section 5.5.7.1 of [ICA]: after
   client authentication, the key proof, and the fingerprint, the IdP
   returns the grant it issued if that grant is unexpired, neither the
   hop nor an ancestor is revoked, and the chain has not ended,
   including under Section 9.  No other step of this section applies, so
   recovery consumes no limit, and a client whose response was lost
   recovers even the last continuation that a hop-count limit permits.

6.5.  Onward Grants

   The response follows Section 5.5.4 of [ICA], with issued_token_type
   equal to the requested grant type and no refresh token.  Every onward
   grant carries the common claims of "Common Grant Claims, Lifetime,
   and Response" in [FEDERATION], a fresh child handle under Section 4
   of [ICA], and cnf.jkt for the key proven in the request
   (Section 5.5.2 of [ICA]).  The configured grant lifetime limit of
   "Common Grant Claims, Lifetime, and Response" in [FEDERATION]
   applies.  The lifetime bounds that [FEDERATION] derives from a
   subject credential and an agent-resolution input do not apply to
   continuation, and the assertion's expiration does not cap the onward
   grant.  An onward WAG MUST NOT outlive the absolute expiration of its
   chain's agent session.

6.5.1.  Identity Preservation

   The IdP MUST construct every onward grant of a governed chain so
   that:

   *  it is the chain's grant type: an ID-JAG for a delegated chain and
      a WAG for a self-acting chain;

   *  it names the chain's Agent Principal: in an ID-JAG as the single
      act object, with the IdP issuer as iss and the Agent Principal
      identifier as sub, and in a WAG as iss and sub, with no act;

   *  for a delegated chain, it names the chain's user, resolved for the
      target RAS;

   *  its client_id identifies the continuing client's registration at
      the target RAS ("Issuance Prerequisites" in [FEDERATION]); and

   *  it lists the chain's continuing clients in continuation_via
      (Section 6.5.2).

   Where a target RAS distinguishes delegated and self-acting tokens by
   client registration ("Profile Applicability" under "Access at the
   Resource Server" in [FEDERATION]), the IdP selects the continuing
   client's registration there by the chain's acting relationship.

   The continuing client MUST NOT appear in the onward grant's act; it
   appears as the grant's client and in continuation_via, which disclose
   it without making it an actor.  The IdP takes the Agent Principal,
   the user, and the acting relationship from its chain record, never
   from the assertion or the request, so the assertion's act never
   becomes the governed actor.

   Continuation never converts the acting relationship.  The IdP MUST
   NOT issue a WAG from a delegated chain or an ID-JAG from a self-
   acting chain.  For a chain established without this document, it MUST
   NOT issue a governed onward grant, and for a governed chain it MUST
   NOT issue an onward ID-JAG whose act is constructed under
   Section 5.5.5 of [ICA].  Section 12.2 explains the choice.

6.5.2.  Path Disclosure

   Every onward grant of a governed chain discloses the continuing
   clients it passed through, as intermediaries rather than actors, in
   this claim:

   continuation_via:  A JSON array of the canonical actor identities
      (Section 5.5.2 of [ICA]) of the continuing clients that created
      the hops after the root, on the branch from the root to the hop
      being issued, oldest first, so that the last entry is the current
      continuing client.  Each entry is a JSON object with iss and sub
      string members; a recipient ignores other members.  The root hop
      contributes no entry, so the root client appears only if it later
      continues the chain.

   The IdP MUST include continuation_via in every onward grant of a
   governed chain and MUST derive it from its hop records, never from
   the assertion or the request, following the lineage rules of
   Section 5.5.5 of [ICA]: parent references are immutable, and sibling
   branches are excluded.  It takes one entry from each hop after the
   root, then merges consecutive identical entries.  For example, with
   root client A, continuing clients B and then A give [B, A]; A
   continuing twice gives [A]; and A and then B give [A, B].  The list
   is complete.  Policy that narrows the disclosed depth of act under
   [ICA] does not narrow it, because a forwarding intermediary is
   disclosed, never hidden.  The last entry and client_id identify the
   same continuing client, the entry by its canonical actor identity and
   client_id by its registration at the target.

   A recipient MUST NOT treat an entry as an actor: entries are not
   subject to the actor gate and authorize nothing.  A target RAS MAY
   use the list in its own policy, for example to admit agents only
   through approved gateways.

   A target RAS supports path disclosure when trusted configuration
   between it and the IdP establishes that it does; this document
   defines no metadata for it.  A target RAS that supports path
   disclosure MUST convey continuation_via unchanged in every access
   token or introspection response it issues from the onward grant,
   including access tokens it issues on refresh ("Optional RAS Refresh
   Tokens" in [FEDERATION]), so that the API receives it.  A target RAS
   that does not support it still accepts onward grants under
   [FEDERATION] and ignores the claim.

   Where the chain authorization, the continuing client's Continuation
   Association, or policy for the target requires path disclosure, the
   IdP MUST NOT issue an onward grant for a target RAS not established
   to support it (Section 6.6); issuing it would present a path that the
   target discards as if it were complete.  A RAS or API MUST NOT read
   the absence of continuation_via as evidence that no continuing client
   was involved, unless trusted configuration establishes that the RAS
   that issued its token supports path disclosure.

   after any Retry-After interval, with a fresh client assertion and
   DPoP proof as the retry rule of "Dedicated Client Identity" in
   [FEDERATION] requires; otherwise it obtains a fresh assertion.  It
   MUST NOT treat a temporary refusal as the end of the chain.

7.  Onward Redemption and Access

   The continuing client redeems the onward grant under "Redemption
   Request" in [FEDERATION]: the urn:ietf:params:oauth:grant-type:jwt-
   bearer grant type, client authentication as the client the grant
   names, and a DPoP proof of the grant's cnf key.  For governed chains,
   this replaces the jwt-dpop redemption of Section 5.5.5 of [ICA];
   Section 4.4 of [ID-JAG] requires jwt-bearer, and [FEDERATION] applies
   the grant confirmation checks of ID-JAG to it.  Every onward grant
   carries cnf, so the target RAS needs DPoP support at its token
   endpoint ("Grant Protection" in [FEDERATION]), which the continuing
   client verifies under "Capability Discovery" in [FEDERATION].

   The target RAS and API process the onward grant and the resulting
   access token as for any governed grant ("Grant Redemption at the RAS"
   and "Access at the Resource Server" in [FEDERATION]).  They see the
   same Agent Principal, and for delegated access the same user and
   actor gate, as for the agent's own client; only client_id and
   continuation_via name continuing clients, and resource policy can
   permit or deny an agent's access through a particular client or path.
   A RAS that does not implement [ICA] ignores the handle.  One that
   does binds it and applies Section 4, so that a gateway in its domain
   can continue the chain as a further hop that again names the same
   agent.

8.  Gateway Requirements

   This section collects what a gateway does as a continuing client; the
   rules of the IdP and the RASes it relies on are in the sections
   cited.  [GUIDE] describes gateway configuration and topologies.

   To continue a request, a gateway:

   1.  processes the incoming access token as the API ("Access at the
       Resource Server" in [FEDERATION]), including the actor gate;

   2.  obtains an assertion from the CAI with that request's own token,
       as below (Appendix A.2 shows the request);

   3.  verifies the target's capabilities and requests the chain's grant
       type from the IdP (Section 6.1, Appendix A.3);

   4.  redeems the onward grant with jwt-bearer and a proof of its key
       (Section 7);

   5.  reuses downstream tokens only within the same context and source
       hop; and

   6.  handles errors without falling back, as below.

   The CAI binds the assertion to the handle of the token the gateway
   presents (Section 5.4.3 of [ICA]), but a gateway that holds several
   agents' tokens chooses which to present.  The gateway MUST therefore
   request an assertion only with the access token, or a carrier derived
   from it, of the request it is continuing.

   "Client Token Reuse" in [FEDERATION] applies to every onward grant
   and downstream access token the gateway holds: it reuses one only for
   a request in the same agent, user, tenant, target, authority, and
   proof context.  The gateway MUST also reuse one only for a request
   that arrived on the same source hop.  Two chains can share all of
   that context yet differ in root binding, credential, anchor, and
   revocation, so serving one chain's request with a token obtained on
   another would let it continue after its own chain had ended
   (Section 8 of [ICA]).  Each source hop therefore needs its own
   continuation, once for each target.

   When continuation from a request's source hop fails with
   invalid_continuation, the gateway SHOULD reject the agent's request
   with HTTP 401 and the invalid_token error code of the access token's
   scheme ([RFC6750], [RFC9449]), so that the agent's client obtains a
   new access token from a new root grant.  An access token obtained by
   refresh at the gateway's RAS ("Optional RAS Refresh Tokens" in
   [FEDERATION]) can keep the ended source hop, so continuation from it
   fails again until the agent's client obtains a new root grant.

   A limit failure (invalid_grant) does not end the chain, and a new
   access token can lead to a source hop that fails the same way, as
   when an upstream gateway continues again into the same chain and
   reaches the same hop count or depth.  The gateway MUST NOT reject the
   agent's request with invalid_token solely because continuation failed
   with invalid_grant; it fails the request with an error of its own
   API.  An independent failure to validate the access token still leads
   to invalid_token.  Where deployment-specific information identifies a
   rate limit, the gateway can retry under that limit's policy.  A
   temporary refusal is not an error response: the gateway retries as
   Section 6.6 describes.

   After the IdP rejects a governed continuation for a request, the
   continuing client MUST NOT serve that request with its own authority
   or through a chain established without this document.  This extends
   the no-fallback rule of "Profile Applicability and Downgrade
   Prevention" in [FEDERATION], which covers retrying as ordinary access
   or without proof.  Gateway-side tool filtering narrows what the
   gateway attempts but does not authorize.

10.  Conformance and Capability Advertisement

10.1.  Conformance Claims

   The roles are the IdP, the continuation-aware RAS and its CAI, the
   continuing client, and the target RAS.  An implementation claims
   delegated continuation, self-acting continuation, or both, for each
   role it implements.  Each claim requires the same realization under
   [FEDERATION] and the applicable requirements of [ICA] as this
   document changes them.  A target RAS that does not continue the chain
   implements [FEDERATION] with DPoP support at its token endpoint, and
   nothing from this document unless it supports path disclosure
   (Section 6.5.2).

   An IdP claiming delegated continuation can additionally claim grant-
   anchored continuation.  This claim requires support for refresh-token
   subjects under "Subject Token Validation" in [FEDERATION] and grant
   anchors under Section 6.1 of [ICA].  Such chains can continue after
   the user's session ends, as unattended work needs (Appendix A.7).  A
   delegated continuation claim alone does not guarantee grant-anchor
   support.

   Each claim has this mandatory interoperability path:

   *  *Client authentication:* The continuing client, CAI, IdP, and
      target RAS MUST implement [RFC7523] private_key_jwt client
      authentication, under "Dedicated Client Identity" in [FEDERATION]
      for its audience, replay, and retry rules.

   *  *Proof:* They MUST implement DPoP [RFC9449] with the algorithms of
      "Client Authentication and Algorithms" in [FEDERATION].

   *  *Assertion issuance:* Every CAI that serves a continuing client
      MUST support assertion issuance at its token endpoint with an
      access-token subject_token (Section 5.4.1 of [ICA]), resolving the
      token as Section 5.4.6 of [ICA] describes when the CAI is not the
      accepting RAS.  The continuing client MUST implement that request.

10.2.  Metadata

   A continuation-aware RAS that binds handles of governed grants MUST
   list urn:ietf:params:oauth:grant-profile:governed-agent-continuation
   in authorization_grant_profiles_supported (Section 7.2 of [ID-JAG]),
   together with the governed profile URIs that identify the grants it
   accepts.  The value indicates handle binding under Section 5.2 of
   [ICA] with the access-token protection and eligibility of Section 4,
   and redemption of onward grants with jwt-bearer (Section 7); it does
   not indicate jwt-dpop support.  A RAS lists ICA's
   urn:ietf:params:oauth:grant-profile:id-jag-continuation, with the
   requirements of Section 7.2 of [ICA], only if it also binds handles
   of chains established without this document.  As for the self-acting
   profile URIs of [FEDERATION], use of this parameter for WAGs awaits
   coordination (Appendix B.3).

   An IdP that supports delegated continuation advertises
   identity_continuation_supported (Section 7.1 of [ICA]), which
   indicates continuation-capable ID-JAG issuance; an IdP that supports
   only self-acting continuation does not.  Support for self-acting
   continuation is established through trusted configuration
   ("Capability Discovery" in [FEDERATION]); no IdP metadata advertises
   it.  The same holds for grant-anchored continuation (Section 10.1).
   Advertisement indicates capability and does not authorize
   continuation.

11.  Implementation Considerations

   These considerations add no requirements.  They describe deployment
   choices that decide whether continuation works as the sections cited
   intend.

11.1.  Identity Provider

   *  *Continuation window:* To keep continuation available throughout
      the authorization that the accepting RAS derives from a hop, a
      deployment sizes the window of Section 3.1 to cover the redemption
      window of the grant that carries the hop's handle, plus the
      lifetime of the access tokens, and of any refresh authorization,
      that the RAS issues for it.  A shorter window limits how long a
      compromised CAI can use the hop (Section 12.1).  Its cost is that
      the IdP rejects new continuation requests from a hop whose tokens
      are still accepted, and the gateway fails those requests without
      prompting a new root grant (Section 8).  A deployment whose
      gateway or client continues from durable task state sets the
      window to the task's needs, as in Appendix A.7.  This document
      sets no default.  Lengthening the window does not extend the
      deadlines of hops already issued, so it cannot restore
      continuation from a hop whose deadline has passed.  Continuation
      can still proceed from a later hop within its own deadline; a task
      with no such hop, such as the scheduled variant once H0's deadline
      passes, needs a new chain.

   *  *Agent sessions:* A working agent obtains a new WAG at least as
      often as its gateway access token expires, since WAG redemption
      yields no refresh token, so a deployment sets the idle timeout
      longer than that token's lifetime.  If the token outlives the
      session, continuation fails, and the gateway's response leads the
      agent's client to a new root grant (Section 8).  Work that a
      gateway performs after the agent stops authenticating, such as
      queued work, loses continuation at the idle timeout; work that
      must outlive the agent's authentication needs a durable anchor
      (Appendix B.4).

   *  *Restored relationships:* The IdP can determine whether a change
      ended a chain when it applies the change or at the next
      continuation, for example by comparing a revision of each
      relationship, recorded at establishment and changed by every
      disablement or withdrawal (Section 9).

11.2.  Continuing Client

   *  *Several Governance Tenants:* A gateway that serves several
      Governance Tenants is configured in each, because [ICA] scopes
      actor identities and CAI trust to one tenant.  How it selects
      among those registrations is an open item (Appendix B.4).

12.  Security Considerations

   The security considerations of [ICA] and [FEDERATION] apply.

12.1.  Gateway Compromise

   A compromised gateway that can still authenticate and prove its key
   can continue each chain whose access token it has received, to any
   target that the chain authorization, the agent's current
   authorization, and its Continuation Associations permit, and can use
   the downstream tokens it holds until they expire.  Where its operator
   does not control the CAI, it cannot continue a chain whose token it
   has not received, because the CAI attests only hops bound to tokens
   presented to it (Section 5.4.3 of [ICA]).  Where its operator runs
   the CAI, as when the gateway's own RAS performs that role, the CAI
   can attest any hop its RAS accepted, as Section 9.5 of [ICA] notes
   for a compromised RAS, until the chain ends or the hop's continuation
   window passes.  In either case it cannot change the agent or user,
   convert the acting relationship, or exceed the agent's own
   authorization.  The window does not bound the chain: where policy
   permits continuation to a target whose RAS the operator also runs,
   each hop accepted there has a window of its own, and only the hop-
   count limit of Section 6.3 of [ICA] bounds how far the operator can
   extend the chain.  Narrow Continuation Associations, chain
   authorizations that restrict targets, a short continuation window,
   short downstream token lifetimes, and sender-constrained ingress
   reduce the exposure; the last also keeps a stolen bearer token at the
   gateway from inducing an honest continuation (Section 9.1 of [ICA],
   Section 4).

12.2.  The Continuing Client Is Not an Actor

   Placing the gateway in act, as Section 5.5.5 of [ICA] does for the
   current actor, would give every agent behind a gateway the same
   outermost actor, recreating at the actor level the shared-client
   problem.  A governed RAS and API would have to process nested act,
   which [FEDERATION] rejects, and a WAG, which carries no act, could
   not represent the gateway at all.

   The agent acts for the user, and the gateway forwards the agent's
   request.  A forwarding intermediary is still disclosed, in
   continuation_via, so attribution and path-based policy need no
   lineage in act.

   The user's approval reaches the gateway through the Delegation
   Authorization, which must permit continuation for a delegated chain
   to exist.  Continuation never turns a delegated chain into a WAG,
   which would let an agent act on its own authority because a user's
   request reached it.

12.3.  Attribution Through an Intermediary

   Downstream records attribute an action to the Agent Principal and,
   for delegated access, the user, with the continuing client as
   client_id and every continuing client on the path in
   continuation_via.  A target RAS can therefore audit and authorize the
   path without consulting the IdP, and so can an API whose RAS supports
   path disclosure; the IdP's hop records remain authoritative.  A
   handle does not distinguish a root grant from an onward grant; a
   resource that must tell a gateway from the agent's own client uses
   the authenticated client_id or the presence of continuation_via,
   which only onward grants carry.

12.4.  Self-Acting Chains

   [ICA] anchors a chain to state showing that its principal is still
   present and records what the chain may do separately.  An Agent
   Authorization is often indefinite, so as an anchor it cannot tell a
   working agent from one that has stopped; a dedicated-client assertion
   lasts one request, and routine credential rotation would end chains.
   Only the agent's own authentication refreshes an agent session, so a
   gateway cannot extend a chain it continues, and keeping it per
   Identity Binding stops activity on one platform from sustaining
   chains rooted through another.  The absolute expiration bounds a
   session the agent keeps active, as the absolute authorization
   expiration of "Optional RAS Refresh Tokens" in [FEDERATION] bounds
   refresh; without it, a chain would substitute for the refresh token
   that [WAG] prohibits.

   When an agent stops authenticating through a binding, its self-acting
   chains through that binding end within the idle timeout without
   administrative action.  A party holding the agent's credential can
   keep its session active, as a stolen user credential can keep a user
   session active, until the absolute expiration or the credential's
   revocation (Section 9).

12.5.  Induced Continuation

   An agent induced to misuse its authority ("Misuse by an Authorized
   Agent" in [FEDERATION]) can ask a gateway to continue its request to
   any target its chain permits.  The scope of the agent's access token
   at the gateway does not limit that authority, as [ICA] notes for
   incoming access-token scopes.  The chain authorization, the agent's
   current Delegation or Agent Authorization, and the continuing
   client's Continuation Association bound each onward grant instead
   (Section 6.4), and the target applies its own authorization.  A
   deployment that needs onward authority narrower than the agent's
   authorization records narrower restrictions in the chain
   authorization or the Continuation Association.

12.6.  Governance Events End the Chain

   The root's Identity Binding, Client Association, and credential are
   the chain's only link between the agent and an authenticated client.
   When any is withdrawn, the chain has no current basis, even if
   another binding resolves the same agent for new issuance.  An ended
   chain stays ended, as in Section 6.2 of [ICA], and reactivation
   permits new decisions only, as in [FEDERATION].

12.7.  Disablement Windows

   Issued onward grants and downstream access tokens, including those a
   gateway has cached, remain usable after a chain ends until they
   expire or their revocation is applied.  A refresh token that a target
   RAS issues under "Optional RAS Refresh Tokens" in [FEDERATION]
   extends access further; a deployment that relies on chain ending
   configures its targets not to issue refresh tokens to continuing
   clients, so that renewal is another continuation.

13.  Privacy Considerations

   The privacy considerations of [ICA] and [FEDERATION] apply.
   Continuation discloses the Agent Principal identifier to each target
   the gateway reaches, extending the cross-resource correlation that a
   stable agent identifier allows, and the gateway learns which agents
   and users call which tools.  An onward grant discloses every
   continuing client on the path, as Section 5.5.5 of [ICA] would, but
   as intermediaries rather than actors, and it does not disclose the
   root client.  The IdP's hop records hold the complete path and are
   sensitive audit data.

   This non-normative walkthrough adds a gateway to the dedicated-client
   walkthrough of [FEDERATION] and reuses its identities: the client
   analysis-client, the Agent Principal agent-42, the user Alice, and
   the resource https://api.example/tenants/acme-data/ at
   https://ras.example/, where Alice is alice-ras to the IdP and

   The gateway is an MCP gateway at https://gateway.example/mcp, whose
   operator runs https://ras.gateway.example/ as its RAS and CAI.

A.6.  Two-Gateway Variant

   Here tool-gateway reaches the file service through a second gateway,
   data-gateway at https://data-gateway.example/, whose RAS is

   data-gateway as it does tool-gateway, with canonical actor identity

   data-files at https://ras.example/; D is its DPoP key.

   child hop H1. data-gateway then obtains an assertion for H1 and
   continues to https://ras.example/. The onward ID-JAG (excerpt):

     "client_id": "data-files",

A.7.  Scheduled Variant

   Here agent-42 prepares a daily report for Alice after she has signed
   out, without a gateway.  The client uses Alice's refresh token once
   to establish the chain.  Later runs authenticate the client and
   continue from server-held task state.

   The agent's operator runs https://ras.agents.example/ as a
   continuation-aware RAS and CAI for its task service
   https://agents.example/tasks, where the agent's client is analysis-
   tasks and Alice is alice-tasks to the IdP.  The IdP claims grant-
   anchored continuation (Section 10.1), and the deployment supports
   durable task authorization, with Transaction Tokens carrying each
   scheduled run's context; an IdP without grant-anchor support issues
   the root ID-JAG without a handle (Section 6.1 of [ICA]).  The IdP
   accepts refresh-token subjects from analysis-client ("Subject Token
   Validation" in [FEDERATION]), trusts AgentRAS as CAI for its own
   hops, and has a Continuation Association that permits analysis-client
   to continue agent-42's delegated chains to resources in acme-data.
   analysis-client has the default canonical actor identity of
   Section 5.5.2 of [ICA], (https://idp.example/, analysis-client), so
   the IdP pairs AgentRAS with itself as the client's identity
   authority.

A.7.1.  One-Time Setup

   While Alice is signed in, she asks for the report.  The client holds
   a refresh token that the IdP issued to analysis-client for Alice,
   whose grant has her Delegation Authorization for agent-42 explicitly
   associated.  It presents that refresh token as the subject_token,
   with subject_token_type urn:ietf:params:oauth:token-
   type:refresh_token, for audience https://ras.agents.example/,
   resource https://agents.example/tasks, and scope tasks.run.  The IdP
   anchors the chain to the refresh token's grant, not to Alice's
   session (Section 6.1 of [ICA]).  The root ID-JAG (excerpt):

   {
     "sub": "alice-tasks",
     "aud": "https://ras.agents.example/",
     "client_id": "analysis-tasks",
     "resource": "https://agents.example/tasks",
     "scope": "tasks.run",
     "auth_time": 1789646400,
     "act": {"iss": "https://idp.example/", "sub": "agent-42"},
     "cnf": {"jkt": "JKT_K"},
     "identity_continuation_handle": "Wd4nKs8QpZ2vXe6TbR1mLy"
   }

   The client redeems it at AgentRAS with a proof of K.  AgentRAS binds
   the handle, H0, to a task record that holds no bearer credential and
   designates analysis-client to run the task (illustrative):

   task_id:   task-7
   user:      alice-tasks
   agent:     agent-42
   runner:    analysis-client
   handle:    Wd4nKs8QpZ2vXe6TbR1mLy   # H0
   schedule:  daily at 06:00 UTC
   status:    active

   The client does not need the refresh token for this task again.
   Every run continues from H0, so the deployment sets the continuation
   window (Section 3.1) to the task's duration.

A.7.2.  Each Scheduled Run

   At 06:00 UTC the next day, with Alice signed out, the platform's
   scheduler starts a run that names only task-7.  The run has no
   incoming request: it continues from the task's hop under the
   scheduled-run carrier of Section 5.3 of [ICA].  The client,
   authenticating to AgentRAS, names task-7; AgentRAS derives H0 from
   the active task record for which analysis-client is designated into a
   Transaction Token for the run, as in Appendix B.3 of [ICA], and the
   client exchanges it at AgentRAS's token endpoint for an assertion
   bound to K.  The client then requests an ID-JAG from the IdP for
   https://ras.example/, resource https://api.example/tenants/acme-
   data/, and scope files.read.

   The continuation exchange performs no agent resolution: the agent
   comes from the chain record, not from analysis-client's Identity
   Binding (Section 6.2).  The refresh-token grant anchoring the chain
   remains active, even though the root ID-JAG's redemption window has
   expired.  The Continuation Association permits analysis-client, and
   Alice's Delegation Authorization permits agent-42 to act for her with
   files.read.  The onward ID-JAG (excerpt):

   {
     "sub": "alice-ras",
     "aud": "https://ras.example/",
     "iat": 1789711205,
     "exp": 1789711505,
     "client_id": "analysis-api",
     "resource": "https://api.example/tenants/acme-data/",
     "scope": "files.read",
     "auth_time": 1789646400,
     "act": {"iss": "https://idp.example/", "sub": "agent-42"},
     "continuation_via": [
       {"iss": "https://idp.example/", "sub": "analysis-client"}
     ],
     "cnf": {"jkt": "JKT_K"},
     "identity_continuation_handle": "Hc7rVm3NxT9kQw5ZpB2sJf"
   }

   Its sub, act, and client_id are those of the grant in the walkthrough
   of [FEDERATION], so https://ras.example/ processes it as before, and
   the API sees agent-42 acting for Alice.  Its auth_time is still
   Alice's sign-in of the previous day, carried unchanged from the root
   (Section 5.5.5 of [ICA]). continuation_via names analysis-client
   because the root client continued the chain; the root hop itself
   contributes no entry (Section 6.5.2).

   Runs need no retained user credential.  Each creates a new child of
   H0 and obtains a short-lived, sender-constrained assertion and onward
   grant, both bound to K.

A.7.3.  Withdrawal

   If Alice withdraws her Delegation Authorization for agent-42, the
   chain ends and the next run fails (Appendix A.8), while her
   delegations to other agents continue.  Revoking the refresh-token
   grant that anchors the chain also ends it (Section 6.2 of [ICA]).

B.4.  Open Items

   [[ To be removed before publication as an RFC ]]

   1.  *Home of continuation_via:* Should [ICA] define it, with an
       acting or forwarding mode for each hop, so that this document
       uses ICA's claim instead of its own?  Should policy ever be able
       to narrow it, as it can narrow the depth of act (Section 6.5.2)?

   2.  *Self-acting discovery:* Should the IdP advertise support for
       self-acting continuation in metadata?

   3.  *Agent session limits:* Should this document recommend default
       idle and absolute limits for agent sessions, and convey a
       session's expiration to the gateway so that long-running work can
       obtain a new root before it?

   4.  *Continuation Association management:* Should [AGENT-MANAGEMENT]
       model Continuation Associations beside Client Associations?

   5.  *Durable self-acting anchors:* Should a self-acting chain be able
       to anchor to a work authorization with its own lifecycle, as a
       delegated chain can anchor to a refresh-token grant
       (Section 12.4)?

   6.  *Tenant selection at a gateway:* How does a gateway that serves
       several Governance Tenants select its registration and credential
       at the IdP, when neither its incoming token nor the assertion
       response names the Governance Tenant?

   7.  *Temporary refusals:* Should [ICA] adopt the same HTTP 503
       response for state it cannot confirm, and define an OAuth error
       code for policy that blocks a chain only temporarily
       (Section 6.6)?
