         Human Oversight Profile for Governed Agent Federation
         draft-mcguinness-oauth-governed-agent-oversight-latest

Abstract

   The OAuth 2.0 Profile for Governed Agent Federation decides which
   governed agent acts, for whom, and under what authorization, and an
   identity provider issues the resulting grant without a person
   present.  It bounds what an external approval can do but leaves
   asynchronous approval undefined.

   This document defines three oversight modes for governed agent
   access.  With a human in the loop, an authenticated person decides on
   the exact governed request before a grant issues or an action
   executes.  With a human on the loop, grants issue at once, but each
   can be observed and ended with a defined effect within a documented
   bound.  With the human out of the loop, standing authorization
   applies with no per-request decision.  The document profiles OAuth
   Deferred Token Response so that an identity provider can hold a
   governed grant until a person decides, binds that decision to the
   resolved agent, user, client, target, authority, and proof key, and
   requires the grant that follows to be the one the request would have
   produced.  It also describes how Model Context Protocol servers hold
   tool calls under these modes.

1.  Introduction

   Under [FEDERATION], an identity provider (IdP) issues a governed
   grant when a Delegation Authorization or an Agent Authorization
   permits the request.  The basis of those authorizations is a
   deployment choice: administrator assignment, organizational policy,
   task authorization, or user consent ("Authorization Relationships" in
   [FEDERATION]).  Each is decided before the request arrives.  Many
   deployments also need a person to decide at the moment an agent asks
   for something sensitive, or at least to see each grant as it issues
   and be able to stop it.

   The pieces for that exist separately.  OAuth Deferred Token Response
   [DTR] lets a token endpoint answer later.  OpenID Client-Initiated
   Backchannel Authentication [CIBA] reaches a person out of band.
   AuthZEN's access request profiles route an approval and complete it
   as a token ([ARAP], [AROP]).  Model Context Protocol [MCP] servers
   can hold a tool call while they wait.  None of them says which agent,
   user, and authority an approval covers when the requester is a
   governed agent, or what grant follows it.  [DTR] does not say that
   the token it eventually returns keeps the original subject, actor, or
   client.

   [FEDERATION] answers who acts, for whom, and under what
   authorization.  [DTR] answers how a token endpoint waits.  This
   document answers when a person must decide, what the decision binds
   to, and what grant follows it.  It defines:

   *  three oversight modes, and how policy selects them (Section 3);

   *  deferred governed issuance: the pending request, who may approve
      it, what an approval can change, and the checks and grant at
      resolution (Section 4);

   *  supervised issuance: what an IdP and a deployment must provide
      before claiming that a person can observe and end each grant
      (Section 5);

   *  per-action oversight at a resource, within the authority of the
      access token (Section 6).

   Section 7 describes how Model Context Protocol servers realize these
   modes; that section is informative.

1.1.  Protocol Overview

   An agent acting for Alice asks for authority that policy says Alice
   must approve.  The client opts in to deferral, and the IdP holds the
   request until Alice decides.

   Client          IdP              Alice            RAS
     |              |                 |                |
     | (1) exchange, completion_mode=deferred, DPoP K  |
     |------------->|                 |                |
     | (2) authorization_pending, deferral_code        |
     |<-------------|                 |                |
     |              | (3) approval request (agent, user,
     |              |     client, target, authority)   |
     |              |---------------->|                |
     |              |<----------------|                |
     | (4) poll with deferral_code, DPoP K             |
     |------------->|                 |                |
     | (5) ID-JAG for the approved authority, cnf K    |
     |<-------------|                 |                |
     | (6) redeem as any governed grant                |
     |-------------------------------------------------->|

                    Figure 1: Deferred governed issuance

   1.  The client sends a governed token exchange request with
       completion_mode=deferred and a DPoP proof (Section 4.1).

   2.  The IdP completes every issuance check except Alice's decision,
       records the pending request, and returns a deferred response
       (Section 4.2).

   3.  Alice authenticates and approves the request, or a narrower one,
       through a channel this document does not define (Section 4.3).

   4.  The client polls with the deferral code, proving the same key.

   5.  The IdP re-checks the request and issues the governed grant the
       request would have produced, for the approved authority and bound
       to the same key (Section 4.4).

   6.  The RAS processes the grant as any governed grant under
       [FEDERATION].

1.2.  Scope

   This document covers governed grant issuance at the IdP, including
   continuation ([CONTINUATION]), and oversight of individual actions at
   an API.  It does not cover:

   *  approval of a task, which Mission-Bound Authorization addresses
      ([MISSION-APPROVAL]);

   *  multi-party approval or the provenance of an approver's authority;

   *  the approval channel or its user interface;

   *  the format or transport of notices to overseers;

   *  deferral of grant redemption at the RAS, or completion of an
      approved access request as a token under [AROP] (Appendix C).

   This document defines no new token format, claim, error code, grant
   type, or request parameter.

2.  Conventions and Terminology

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   Agent Principal, Identity Binding, Client Association, acting
   relationship, Delegation Authorization, Agent Authorization,
   Governance Tenant, Target Tenant, actor gate, and resource
   authorization server (RAS) follow [FEDERATION].  ID-JAG and WAG [WAG]
   refer to the grants as [FEDERATION] profiles them.  Deferral code,
   deferred response, completion mode, and originating grant follow
   [DTR].  Local Suspension and grant-derived revocation follow
   [AGENT-LIFECYCLE].

   This document defines these terms:

   Oversight mode:  The policy that determines whether a person decides
      on a governed request before a grant issues or an action executes
      (human in the loop), may observe and end what was issued (human on
      the loop), or is not involved per request (human out of the loop)
      (Section 3).

   Approver:  A person who decides on a pending governed request or a
      held action, acting within authority over it that the person held
      before the request.  An agent, a client, a policy engine, or
      another automated system is not an approver.

   Overseer:  A person who can observe grants issued under supervised
      issuance and can intervene (Section 5).

   Governed request context:  For a governed token exchange request, the
      resolved Agent Principal; for delegated access, the resolved user;
      the authenticated client and its registration at the target RAS;
      the acting relationship; the Governance and Target Tenants; the
      RAS, resource, and requested authority (scope and any
      authorization details); for a continuation, the continuing client;
      and the request's proof key.

   Pending governed request:  IdP state for a governed token exchange
      request that passed every check of [FEDERATION] except an
      approver's decision.  It holds the request's governed request
      context and is not a credential.

   Intervention:  An action that ends or narrows authority already
      issued: grant-derived revocation, withdrawing or narrowing a
      Delegation or Agent Authorization, a Local Suspension, or
      disabling the agent.

   Intervention bound:  The documented maximum time from an intervention
      until the affected target stops accepting the authority it ends,
      including propagation, caching, and the lifetime of tokens
      accepted without a check.

   |       |                               | or         |              |
   |       |                               | execution  |              |
   |       |                               | waits for  |              |
   +=======+===============================+============+==============+
   | Human | An approver, before the       | The        | Section 4,   |
   | in    | grant issues or the           | approver's | Section 6    |
   | the   | action executes, on its       | decision   |              |
   | loop  | governed request              |            |              |
   |       | context or the action         |            |              |
   +-------+-------------------------------+------------+--------------+
   | Human | No one before issuance;       | Nothing    | Section 5    |
   | on    | an overseer can observe       |            |              |
   | the   | each grant and                |            |              |
   | loop  | intervene                     |            |              |
   +-------+-------------------------------+------------+--------------+

   | the   |                               |            |              |
   | loop  |                               |            |              |
   +-------+-------------------------------+------------+--------------+

                          Table 1: Oversight modes

   These rules apply to every mode:

   *  *Policy selects the mode.* The IdP determines the mode for a
      governed request from trusted policy for the resolved agent,
      acting relationship, user, client, target, and requested
      authority, usually as a condition of the Delegation or Agent
      Authorization.  A request parameter or the client's opt-in to
      deferral MUST NOT select a mode or lower one that policy requires.

   *  *Each decision point applies its own mode.* IdP issuance, IdP
      continuation, and the API's decision on an action each apply the
      mode their policy requires.  Oversight at one point does not
      satisfy another: a resource domain that requires a person to
      decide on an action applies its own human-in-the-loop decision at
      the action (Section 6), as the RAS decides anew under
      [FEDERATION].

   *  *Only a person approves.* A decision by a supervising agent, a
      policy engine, or a risk service can be a condition of issuance,
      but a request decided that way is not human in the loop.

   *  *An approval is not standing authority.* An approval covers the
      one request or action it was made on.  Making it standing
      authority is a change to the Delegation or Agent Authorization,
      made by a principal authorized to make that change; requests
      within the changed authorization are then human out of the loop.

   Human out of the loop is the behavior of [FEDERATION]; this document
   adds no requirement for it.

   In the terms of [OVERSIGHT-ACTS], a human-in-the-loop approval is a
   release: the approver permits a specified request within authority
   held beforehand, and the release establishes that the request was
   permitted, not that it was correct.  A notice under supervised
   issuance supports an observation, and an intervention is a decision.
   This document does not define how such acts are recorded.

4.  Deferred Governed Issuance

   This section profiles [DTR] for governed token exchange requests at
   the IdP: ID-JAG and WAG requests under [FEDERATION], and continuation
   requests under [CONTINUATION].  A pending governed request moves
   through these steps, which the subsections define:

   +=============+============================+=======================+
   | Event       | IdP action                 | Result                |
   +=============+============================+=======================+

   |             | assertion (Section 4.2,    |                       |
   |             | Section 4.5)               |                       |
   +-------------+----------------------------+-----------------------+
   | Poll before | Verifies the client and    | authorization_pending |
   | a decision  | its key                    | or slow_down          |
   +-------------+----------------------------+-----------------------+
   | Approver    | Records the decision for   | Pending until the     |
   | decides     | this request only          | next poll             |
   |             | (Section 4.3)              |                       |
   +-------------+----------------------------+-----------------------+
   | Poll after  | Re-checks the request; for | Grant; reservation    |
   | approval    | a continuation, counts the | ISSUED                |
   |             | grant against the limits   |                       |

   Reservation states apply to a deferred continuation at an IdP that
   offers idempotent retry (Section 4.5).  A pending request holds no
   limit capacity and no grant, so its end releases nothing else.

4.1.  Client Opt-In

   A client that can wait for an approver includes deferred in the
   completion_mode parameter of its token exchange request (Section 4.1
   of [DTR]).  It MUST present a DPoP proof [RFC9449] on that request,
   whatever its client authentication method.  This narrows Section 10.1
   of [DTR], which lets a confidential client using private_key_jwt omit
   DPoP: under this document the deferral code and the grant it yields
   are bound to one key.

   When policy requires human in the loop and the request does not
   include deferred, the IdP MUST NOT return a deferred response
   (Section 4.1 of [DTR]) and MUST NOT issue the grant.  It rejects the
   request (Section 5.2 of [RFC6749]) with actor_unauthorized for
   delegated issuance or invalid_target for self-acting issuance.  These
   are the errors [FEDERATION] assigns when approval requires a
   condition the selected composition cannot enforce ("Issuance
   Authorization" in [FEDERATION]); this document reuses them for an
   approval that the request did not let the IdP obtain.  This document
   defines no discovery of a target's oversight mode; a client learns to
   opt in from configuration or from a pre-token hint (Section 4.2 of
   [DTR]).

4.2.  Deferring

   Before returning a deferred response, the IdP MUST complete every
   check that [FEDERATION] requires for the request except the
   approver's decision: client authentication, agent resolution, the
   Client Association, subject validation and resolution, the Delegation
   or Agent Authorization, target and tenant resolution, and the client
   registration association.  A request that fails a check is rejected
   as [FEDERATION] specifies and is not deferred.  An approver therefore
   never decides on a request the IdP would refuse.

   The IdP then records a pending governed request holding the request's
   governed request context, and returns the deferred response of
   Section 5.4 of [DTR].  The deferral code represents that pending
   governed request and nothing else.  The IdP MUST bind it to the
   authenticated client and to the key of the request's DPoP proof, and
   MUST reject a poll or cancellation that does not prove that key
   (Section 10.1 of [DTR]).  The IdP MUST set expires_in no greater than
   a configured maximum pending lifetime for the applicable policy.

   The client does not present the subject token or the agent-resolution
   input again; the IdP validates them when it receives the request.
   The lifetime limits of [FEDERATION] still bound the grant issued at
   resolution: an ID-JAG does not outlive its subject credential ("Grant
   Issuance" in [FEDERATION]), and no grant outlives an agent-resolution
   input that bounds it, such as a platform JWT ("Common Grant Claims,
   Lifetime, and Response" in [FEDERATION]).  For root issuance, the IdP
   MUST set expires_in so that the pending governed request ends no
   later than the earliest of those expirations.  An approval late in
   the window therefore yields a shorter grant.  A deployment that needs
   a longer window uses a subject credential that expires later, such as
   a refresh token.

4.3.  Approval

   The IdP MUST present a pending governed request only to approvers
   that policy designates for it, and MUST authenticate an approver at
   the strength that policy requires.  For delegated access, an approver
   is the user or a person whom policy authorizes to decide for that
   user and target.  For self-acting access, an approver is a person
   policy designates, such as the agent's accountable owner.  The IdP
   MUST NOT accept a decision from the requesting client, the agent, or
   another agent.

   The IdP MUST show the approver the governed request context: the
   agent, the user for delegated access, the client, the target RAS and
   resource, the requested authority, and, for a continuation, the
   continuing client.  Text that the client or agent supplies, such as a
   stated reason, MUST be shown as supplied by the requester and MUST
   NOT replace or restate the governed request context.

   An approver can approve the request as shown, approve a narrower
   authority, or deny it.  An approval MUST NOT widen the governed
   request context: a different agent, user, client, target, resource,
   or acting relationship, or broader authority, needs a new request.
   An approval of narrower authority yields a grant with that authority,
   as [RFC8693] and "Issuance Authorization" in [FEDERATION] permit, and
   the token response's scope reports it.

   An approval covers only the pending governed request it was made on.
   The IdP MUST NOT apply it to another request, including a later
   request with the same governed request context.

   An approver can condition an approval on time.  The IdP enforces such
   a condition only on the grant it issues.  It MUST NOT treat a
   condition on downstream access as enforced, since [FEDERATION]
   defines no portable deadline on authorization a RAS issues and
   rejects issuance whose approval requires a downstream condition the
   composition cannot enforce.

   This document does not define the approval channel.  [CIBA], with a
   binding_message that describes the request, is one way to reach the
   user; an access request service under [ARAP] is another.

4.4.  Resolution

   Before issuing a grant in response to a poll, the IdP MUST re-
   evaluate the request under Section 10.7 of [DTR] and, in addition,
   MUST confirm that:

   *  the Agent Principal is active;

   *  for root issuance, the Identity Binding and Client Association
      used still permit the request;

   *  the Delegation or Agent Authorization still permits the approved
      authority;

   *  for delegated access, the user is active and resolves as before;

   *  for a continuation, neither the presented hop nor an ancestor is
      revoked, the chain has not ended, a Continuation Association still
      permits the continuing client, and the continuation is within the
      limits of Section 6.3 of [ICA] (Section 4.5); and

   *  no change applied within the IdP's freshness limit ("Issuance
      Authorization" in [FEDERATION]) withdraws any of these.

   If any check fails, the IdP returns access_denied and issues no
   grant, as Section 10.7 of [DTR] requires.  A denial resolves to
   access_denied, and a pending request that outlives expires_in
   resolves to expired_token (Section 5.6 of [DTR]).  A client cancels a
   pending request by revoking its deferral code (Section 7 of [DTR],
   [RFC7009]).

   On success, the IdP MUST issue the governed grant that the request
   would have produced without deferral, with the approved authority:

   *  the same Agent Principal, acting relationship, and, for delegated
      access, user;

   *  the same client registration at the RAS as client_id, target, and
      resource;

   *  cnf.jkt equal to the thumbprint of the request's proof key; and

   *  iat and exp set when the grant issues, so that the grant's
      redemption window begins at resolution, within the lifetime limits
      of [FEDERATION] (Section 4.2).

   The successful polling response carries the issued_token_type of the
   originating request (Section 5.5.2 of [DTR]).  No claim in the grant
   indicates that an approval occurred.  The IdP MAY include the txn
   claim [RFC8417] with an identifier of the approval, for audit
   correlation; a RAS or API MUST NOT treat txn as evidence of approval
   or as authority.

   A client whose pending request is denied or expires MUST NOT retry it
   as self-acting access, under another client, or under a lower
   adoption profile.  A later request for the same authority is a new
   request, and a new approval if policy requires one.

4.5.  Continuation

   A continuation exchange ([CONTINUATION]) can be deferred under this
   section, with the continuing client as the client.  Before deferring,
   the IdP performs every validation step of the continuation exchange,
   including the Continuation Association and the limits of [ICA], and
   reserves the assertion as Section 5.5.7 of [ICA] requires.  The
   pending governed request holds that reservation:

   *  *Retention.* The IdP MUST retain the reservation until the later
      of the request's end and the time Section 5.5.7 of [ICA] requires.

   *  *States.* Where the IdP offers idempotent retry, this document
      replaces one transition of Section 5.5.7.1 of [ICA] for a deferred
      continuation: the reservation stays RESERVED while the request is
      pending, rather than becoming FAILED at the assertion's exp plus
      the permitted clock skew.  It becomes ISSUED when the onward grant
      issues and FAILED when the request ends otherwise, on denial,
      cancellation, expiry, or a failed re-check.

   *  *Retries.* The IdP MUST reject a second presentation of the
      assertion, both while the request is pending and after it ends.
      Recovery (Section 5.5.7.1 of [ICA]) does not apply to an onward
      grant issued at resolution, which only the polling response
      delivers (Section 5.5.2 of [DTR]).

   A continuation exchange performs no agent resolution, so at
   resolution the IdP re-checks the chain and the continuing client's
   Continuation Association rather than an Identity Binding
   (Section 4.4).  The continuation window is evaluated when the request
   is received: it bounds when a continuation can be requested, and the
   maximum pending lifetime bounds how long after that the onward grant
   can issue.  A chain that ended while the request was pending resolves
   to access_denied; the continuing client learns of the ending from its
   next continuation, which fails with invalid_continuation.  While the
   request is pending, the continuing client reports the wait to its own
   caller through its own interface, such as an MCP task (Section 7).

   The limits of Section 6.3 of [ICA] count continuations that have
   issued, not requests, so passing them at deferral reserves no
   capacity.  At resolution, the IdP MUST evaluate them again against
   the continuations issued by then, and MUST count the onward grant
   against them atomically with issuing it, so that continuations
   pending together cannot exceed a limit.  A request that would exceed
   a limit resolves to access_denied.

5.  Supervised Issuance

   Under supervised issuance, the IdP issues governed grants without
   waiting, and a person can observe and end each one.  An IdP claims
   supervised issuance for a target only where both hold:

   *  *Each grant is visible.* For each grant it issues under a
      supervised policy, the IdP makes the grant's iss and jti, its
      governed request context, and its issuance time available to the
      overseers that policy designates, no later than it returns the
      grant.  This document does not define the channel or its format.

   *  *Each grant can be ended.* At least one intervention with a
      defined effect reaches the target, with a documented intervention
      bound:

      -  grant-derived revocation of an ID-JAG where the target
         participates ([AGENT-LIFECYCLE]);

      -  withdrawing or narrowing the Delegation or Agent Authorization,
         which stops new grants and ends or narrows continuation
         ([CONTINUATION]);

      -  a Local Suspension at the target; or

      -  disabling the agent, once the target applies it.

   Revoking one WAG is deployment-specific ([AGENT-LIFECYCLE]), so
   supervised self-acting issuance rests on the other interventions.

   The intervention bound includes tokens already accepted.  An API that
   validates access tokens without a check accepts them until they
   expire, and no intervention reverses an operation already performed.
   A deployment that cannot document an intervention bound for a target
   does not claim supervised issuance for it.

6.  Per-Action Oversight

   Resource policy can require a person to decide on an action, such as
   a tool call, before it executes.  The API holds the action, or
   refuses it in a way that lets the agent request it, until an approver
   decides; the API then executes it only after a new decision on the
   same action.  This oversight applies within the access token's
   authority:

   *  *The approval binds to the action.* It covers the operation, its
      target object, and its arguments, and the access token's subject,
      agent, client, and tenant.  The agent is the validated act for a
      delegated token, and the subject for a token that trusted context
      establishes as self-acting ("Profile Applicability" in
      [FEDERATION]).  A changed action needs a new decision.

   *  *Policy selects the mode.* A tool's declared hint, such as an MCP
      tool annotation, MUST NOT select or lower the mode that resource
      policy requires for an action (Section 7).

   *  *The approver is a person.* Resource policy designates approvers
      as in Section 4.3, and the API MUST NOT accept a decision from the
      client, the agent, or another agent as an approval.

   *  *The approval does not add authority.* It satisfies an additional
      condition within the token's authority and cannot expand it
      ("External Approval" in [FEDERATION]).  An action outside that
      authority needs a new governed grant, which the client requests by
      token exchange and the IdP can defer under Section 4.

   *  *A confirmation is not an approval unless it is bound.* A
      confirmation the client shows in its own interface is not an
      approval under this document.  It becomes one only where the API
      authenticates the person, binds the decision as above, and makes
      the decision itself, consistent with Section 10.7 of [AIMS].

7.  Model Context Protocol

   This section is informative.  An MCP server is the enforcement point
   for each tool call it serves.  It realizes the modes as follows.

   *  *Holding a call.* A server that requires a person to decide on a
      call holds it as a task under the MCP tasks extension [MCP-TASKS],
      which the client declares on the request, reporting working or
      input_required until the approver decides.  [MCP-SEP-2848]
      proposes a standard extension in which a requestable denial
      returns a task that stays working while the approval resolves out
      of band, with an access request service under [ARAP] behind it.

   *  *Reaching the user.* URL-mode elicitation can take the user to an
      approval page while the user is present.  [MCP] requires the
      server to bind the elicitation to the user identified by its
      authorization and states that the elicitation response does not
      authorize.  Under this document, the decision is made on the
      approval page by an authenticated approver and feeds the server's
      decision (Section 6).  A self-acting token has no user to elicit
      from.

   *  *Asking for more authority.* A call outside the token's authority
      can be refused with an insufficient_scope challenge.  The client
      then requests a new governed grant by token exchange, which the
      IdP can defer (Section 4).  [MCP-SEP-2643] proposes structured
      denials that can describe this remediation.

   *  *Tool annotations.* [MCP] defines tool annotations, such as
      destructiveHint, as hints that clients treat as untrusted unless
      the server is trusted.  They do not select or lower a mode
      (Section 3); a deployment can use its own classification of tools
      to require a stricter one.

   *  *Client confirmations.* [MCP] recommends that a person be able to
      deny tool calls and sampling requests in the client.  Such a
      confirmation is client behavior, not an approval under this
      document (Section 6).

9.  Security Considerations

9.1.  Approval Fatigue

   An approver asked too often approves without reading.  Policy that
   places routine requests under human in the loop trains approvers to
   approve.  Deployments can reserve approval for requests whose
   authority warrants it, grant routine authority as standing
   authorization that a person reviews periodically, and limit how many
   pending requests one agent can hold.  Converting an approval into
   standing authority is an authorization change (Section 3), not a side
   effect of approving.

9.2.  Misleading Requests

   An agent can phrase a request to mislead an approver.  The governed
   request context comes from the IdP's resolution, not from the
   request, and the requester's own text is shown as the requester's
   (Section 4.3).  An approver can still be misled about why the
   authority is needed; this document makes the request accurate, not
   the reason.

9.3.  Self-Approval

   An agent that could approve its own requests would remove the person
   the mode requires.  An approver is a person designated by policy, and
   neither the requesting agent, its client, nor another agent can
   approve (Section 4.3, Section 6).  How an IdP or API tells a person's
   decision from an automated one depends on the approval channel, which
   this document does not define; the channel's authentication of the
   approver is what makes the rule enforceable.  A deployment that
   routes decisions to an automated approver is human out of the loop
   and records it as such (Section 3).

9.4.  Stale Approvals

   A decision can come long after the request.  The IdP re-checks the
   agent, its bindings and associations, its authorization, the user,
   and the chain at resolution (Section 4.4), and the grant's lifetime
   starts then.  The maximum pending lifetime, and for root issuance the
   expiration of the credentials the request presented (Section 4.2),
   bound how old a request can be when it is approved.

9.5.  Deferral Codes

   A stolen deferral code could otherwise yield the grant after
   approval.  The code is bound to the client and to a DPoP key
   (Section 4.2), as Section 10.1 of [DTR] requires for clients whose
   profile mandates DPoP, and the grant carries the same key.

9.6.  Downgrade

   A client that omits the opt-in, or retries a denied request another
   way, must not obtain the grant without the approval policy requires.
   Policy selects the mode, a request without the opt-in is refused
   rather than issued (Section 4.1), and a denied or expired request is
   not retried as self-acting access, under another client, or under a
   lower profile (Section 4.4).

9.7.  Supervised Exposure

   Under supervised issuance, an agent acts before anyone reviews the
   grant.  What it does before an overseer intervenes, and before the
   intervention takes effect, cannot be undone.  The intervention bound
   (Section 5) states that window; it does not shorten it.

10.  Privacy Considerations

   An approver sees the agent, the user, the client, the target, and the
   requested authority, and an overseer sees the same for each grant.
   The approval channel and overseer notices therefore carry personal
   data and reveal patterns of an agent's work for a user.  Deployments
   limit what approvers and overseers can see to the requests they are
   designated for, and follow Section 8.3 of [DTR]: progress information
   in a polling response carries no personal data.

Appendix A.  Walkthrough: Approval Before Issuance

   This non-normative walkthrough extends the dedicated-client
   walkthrough of [FEDERATION].  Policy lets agent-42 read files in
   acme-data for Alice without approval, and requires Alice's approval
   before it writes them.  The client asks for files.write.

A.1.  Deferred Request

   The client sends the token exchange request of the [FEDERATION]
   walkthrough with scope=files.write, completion_mode=deferred, and a
   DPoP proof of key K.  The IdP authenticates analysis-client, resolves
   agent-42, checks the Client Association and Alice's Delegation
   Authorization, and finds that policy requires Alice's approval for
   files.write.  Alice's ID Token expires in 65 minutes, so a one-hour
   pending lifetime leaves a grant issued at any point in it its full
   300-second lifetime.  The IdP records the pending governed request
   and responds:

   HTTP/1.1 400 Bad Request
   Content-Type: application/json
   Cache-Control: no-store

   {
     "error": "authorization_pending",
     "deferral_code": "DEFERRAL_CODE",
     "expires_in": 3600,
     "interval": 5
   }

A.2.  Approval

   Alice receives an approval request on her authenticator, sent by CIBA
   with this binding message:

   agent-42 (client analysis-client) asks to write files in acme-data

   She authenticates and approves.

A.3.  Resolution

   The client polls, authenticating as in the [FEDERATION] walkthrough
   and proving K:

   POST /token HTTP/1.1
   Host: idp.example
   Content-Type: application/x-www-form-urlencoded
   DPoP: IDP_DPOP_PROOF

   grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Adeferred
   &deferral_code=DEFERRAL_CODE
   &client_id=analysis-client
   &client_assertion_type=urn%3Aietf%3Aparams%3Aoauth
   %3Aclient-assertion-type%3Ajwt-bearer
   &client_assertion=CLIENT_ASSERTION_2

   The IdP re-checks that agent-42 is active, its binding and
   association still permit the request, Alice's Delegation
   Authorization still permits files.write, and Alice is active.  It
   issues the ID-JAG the request would have produced, with scope
   files.write, sub alice-ras, act naming agent-42, client_id analysis-
   api, cnf.jkt for K, and iat at resolution.  The response carries
   issued_token_type urn:ietf:params:oauth:token-type:id-jag.  The
   client redeems it at the RAS as in the [FEDERATION] walkthrough.

Appendix C.  Open Items

   1.  *Deferred redemption at the RAS.* [AROP] lets the RAS defer when
       an agent redeems a grant.  [DTR] does not name the jwt-bearer
       grant, and a deferred redemption needs rules for the grant's exp
       and the RAS's replay record while pending.  Deferral at the RAS
       is also where [AROP] could compose with governed access: the RAS
       issues the tokens that approved_until bounds, while at the IdP
       that bound is a downstream condition the composition cannot
       enforce ("Issuance Authorization" in [FEDERATION]).

   2.  *Administering the mode.* No attribute records the oversight mode
       on a Delegation or Agent Authorization in the SCIM management
       profile.

   3.  *Overseer notices.* Whether a Shared Signals event should carry
       supervised-issuance notices.

   4.  *Duplicate pending requests.* Whether the IdP should return the
       existing pending request when the same governed request context
       is requested again while one is pending.
